# 踩过的坑与页面结构假设

> 这份文档的用途只有一个：**上游改版时，能在3 分钟内定位到是哪一条假设失效了。**
>
> 取数可行性证据在 `PROBE-FINDINGS.md`（为什么能取到）；
> 本文是反过来——**取不到 / 取错了时怎么查**。
>
> 规则：**每条假设都要能回答「它失效时页面会长什么样」**。
> 答不上来的，说明它还不是假设，只是运气好。

---

## 一、页面结构假设清单（按失效概率排序）

### A1. 苹果规格页用 `role="table"` 的 div 网格，**没有 `<table>`** 🔴高

**现状**：取数侧在 `scripts/sources/apple.mjs`。
页面把规格表渲染成 `<div role="rowgroup">` / `<div role="row">` /
`<div role="cell">` —— **没有 `<table>` 标签**。
段落锚点是 class 里的 `techspecs-section section-{key}`。

**失效症状**：解析出0 行，或所有字段为null（页面能打开，但一个值都读不到）。

**为什么容易踩**：任何针对 `<table>` 或通用表格选择器的写法都会静默返回空——
**不会报错**，只会产出一份全是 null 的快照。

**排查顺序**：
```bash
# 1. 单台重跑，看能不能解析出来
node scripts/sources/apple.mjs --limit 1 --out _work/apple.raw.json --cache _work/apple.cache

# 2. 直接看缓存里的 HTML（缓存按 <slug>.html 命名；_work/ 不入库，
#    本地跑过一次取数才有，CI 上由 actions/cache 恢复）
ls _work/apple.cache/                    # 看到底存了哪几台
grep -oE '\bsection-[a-z0-9][a-z0-9-]*' _work/apple.cache/iphone-17.html | sort -u | wc -l
grep -o 'role="cell"' _work/apple.cache/iphone-17.html | head -1
```

**判断依据**：`section-*` 段落数量**实测三台一致（iphone-16/17/18-pro 均为 54 个）**，
比华为稳定得多。关键 key 样例：`section-capacity`、`section-chip`、`section-display`、`section-size`。

⚠️ **别把 54 当契约记住**。真正要盯的是**相对变化**：
明显少于上次实测值、或 `section-capacity` 这类关键 key 消失了，就是结构变了。
两个脚本的注释里写的「35 个段落」是探针阶段的旧计数，已过时。

### A2. 苹果对比页给出42 款机型的全量矩阵，其中大部分 specs 页已 301 🔴 高

**现状**：`/iphone/compare/` 的内联矩阵是苹果侧唯一的深度来源。
对比页列出 42 款，但 `/{slug}/specs/` 只有 6 条在 sitemap 里，
其余要么 301 跳回 `/iphone/`，要么 404——**且跳转后仍返回 HTTP 200**。

**失效症状**：某台机型突然变成空记录（不是「字段少」，是整台消失）。

**致命细节**：**301 跳回来也是 200。** 不校验 `finalUrl` 就会把手机列表页当成规格页解析，
然后产出一堆 null——但记录本身"成功"了。

**排查顺序**：
```bash
# 便宜预检：看是否 301
curl -sI "https://www.apple.com.cn/iphone/iphone-15/specs/" | grep -i "^HTTP\|^location"
# 便宜预检：对比页正文里没挂链接的机型，specs 页一定是 301/404
```
这条经验复用价值最高：**用对比页正文里有没有链接来预判，省掉 30+ 次注定失败的请求**（冷跑 48s → 6.8s）。

### A3. 苹果价格走 `/shop/mcm/product-price`，endpoint 写在页面 `<head>` 里 🔴 高

**现状**：规格页不给价格。endpoint **不硬编码在 JS 里**，而是：
```html
<link rel="ac:pricing-endpoint" href="/shop/mcm/product-price">
```
`autopricing.built.js` 运行时读它。

**失效症状**：全部 7 台价格变null，或 `missing[]` 变长。

**两个必须记住的细节**：
1. **必须用逗号批量**：`?parts=A&parts=B` 只返回 A —— **静默少数据，不报错**。
2. SKU 级价格要走 `https://www.apple.com.cn/shop/buy-iphone/{slug}`，
   HTML 内联两段 JSON（`products[].price.fullPrice` 与
   `displayValues.prices[...].amountBeforeTradeIn`），两处逐 SKU 一致才算可信。

**排查顺序**（先离线看缓存，不必联网）：
```bash
# endpoint 还在不在（实测缓存里能找到）
grep -o 'ac:pricing-endpoint[^>]*' _work/apple.cache/_compare.html
# 价格通道返回结构是否还对
grep -o '"items":{[^}]\{0,200\}' _work/apple-prices.cache/*.html | head -1
```
endpoint 消失、或 `items` 结构变了，就换通道。

### A4. 华为已停售机型一律 301 跳回列表页，**跳转后仍返回 200** 🔴 高

**现状**：`https://consumer.huawei.com/cn/phones/{model}/specs/`。

**失效症状**：和 A2 一样——整机空记录，而非字段缺失。

**便宜预检（约 460 B）**：
```
GET https://consumer.huawei.com/cn/phones/{model}/specs.model.json
```
`title` 以 `"301"` 开头即已下线。实测 13 款 100% 准。

**边界不是机龄而是「是否仍在售」**：nova13（2024-10）已死，mate-xt（2024-09）还活着。
**别用「发布超过 N 年」推断下架**，这条规则已经不成立。

### A5. 华为目录页 `data-config` 里含完整在售目录 🔴 高

**现状**：`/cn/phones/` 的隐藏 input 带 `data-config`，含 slug + 价格 + productId。

**失效症状**：取数入口拿不到任何机型（整个 pipeline 的华为侧为空）。

**排查**（离线即可）：
```bash
grep -o 'data-config="[^"]\{0,200\}' _work/huawei.cache/*.html | head -1
```
**注意 `data-config` 是 HTML 实体转义的**（`&#34;` = `"`），
直接看会以为是 JSON 坏了——实际上它一直是转义状态。

### A6. 华为用 `li.large-accordion__item` 手风琴结构 🔴 中

**现状**：章节名 `.large-accordion__title` + 字段名 `.large-accordion-subtitle`。
⚠️ **缓存文件按 sha1 命名**（不是 slug），要用 `index.json` 反查：
```bash
node -e "
const i=require('./_work/huawei.cache/index.json');
const e=i.entries.find(x=>x.url.includes('mate70/specs/'));
console.log(e.file, e.status, e.bytes);"
```

**失效症状**：某章节（如「电池」）整体解析不到，其他章节正常。

**排查顺序**：用上面的方法定位文件后数锚点
```bash
grep -c 'large-accordion__title' _work/huawei.cache/<file>.html      # 章节
grep -c 'large-accordion-subtitle' _work/huawei.cache/<file>.html    # 字段
```
**实测参考值**（2026-10-03 实测，注意**不同机型差异很大**）：

| 页面 | 章节 | 字段 |
|---|---|---|
| `mate70/specs/` | 16 | 33 |
| `mate90-pro/specs/` | 19 | 33 |
| `mate-x7/specs/`（折叠屏） | 18 | **8** |

⚠️ **`mate-x7` 只有 8 个字段** —— 所以「字段数少于 N 就是结构变了」这条判据**不成立**，
不同机型本来就在 8–33 之间浮动。判据只能是**关键章节名还在不在**
（`电池` / `屏幕` / `尺寸与重量` 这几个）。

**注意**：折叠屏页面字段构成完全不同（内外屏并存），
`sliceByVariants` 与多形态标注逻辑（`折叠态：6.5 英寸；三屏态：10.2 英寸`）都跟这个假设绑定。

### A7. 字段名靠归一化匹配，不是精确匹配 🟡 中

**现状**：`normalizeKey()` 去掉空格/全角括号/下划线/分隔符，用于「运行内存（RAM）」≈「运行内存」。

**失效症状**：某个字段**静默变成 null**——官网改了字段名，归一化匹配不上。

**排查**：把该机型的 `rawOfficial` 整个打出来看官网用的原始字段名：
```bash
node -e "const d=require('./data/products.json');
const p=d.products.find(x=>x.id==='目标id');
console.log(JSON.stringify(p.rawOfficial,null,1))"
```

**这是「缺数据」类问题最快的排查入口**——`rawOfficial` 里有一切官网原文。

### A8. 电池容量必须带口径（典型值 / 额定值）🟡 中

**现状**：华为写「6800 mAh（典型值）」，额定值常在章节脚注里。

**失效症状**：闸门报「有电池容量但缺 capacityCaliber」。

**为什么这条是硬要求**：口径不可缺失。苹果不公布 mAh（恒为 null），
但华为公布就必须标明是典型还是额定——否则跨机型比较毫无意义。

## 二、解析层的坑（与页面无关，改代码也会踩）

### P1. `\b` 对非 ASCII 无效 🔴

```js
/\b/.test('克')      // false —— 克不是 \w，后面的空格也不是
/g\b|克|gram/        // ✅ 非 ASCII 单位必须单独一支，不加 \b
```
**症状**：中文单位解析全部返回 null（英文单位正常）。

---

### P2. 零宽字符污染机型名 🟡

华为页面把「非凡大师」写成 `非<U+2008>凡<U+2008>大<U+2008>师`，
还有 `&#8203;` 实体形式。**不清掉就没法和别处的机型名对齐**，id 对不上 → 整机数据挂到错误的 key 上。

```js
stripInvisible  // Unicode 区间 + HTML 实体两路都清
```

---

### P3. 「少取一个值」闸门一律放行 🔴 **最危险**

这是本项目最重要的一条认知，两次真实事故都栽在这里：

| 官网原文 | 取错的结果 | 闸门拦得住吗 |
|---|---|---|
| `2160 Hz 高频 PWM 调光` | 刷新率 2160 | ✅ 拦得住（超出 `[48,240]`） |
| `2622 x 1206 像素分辨率` | 刷新率 2622 | ✅ 拦得住 |
| `60 Hz / 90 Hz 屏幕` | **只取到 60**，90Hz 整段丢失 | ❌ **拦不住** |
| `7.44 盎司` | 重量 7.44 g | ❌ 拦不住 |
| `12 GB RAM` 混在 ROM 字段 | 存储档位多出 12 | ❌ 拦不住 |

**凡是「少取了一个值」「取到了相邻字段的值」，结果都落在合理区间内，闸门没有理由拦。**

所以改解析器之前必须跑：
```bash
node scripts/selftest.mjs
```
每个历史事故都有对应断言。这不是形式主义——`60 Hz / 90 Hz` 那个 bug
**是在自测写完当天被抓到的**，靠肉眼不可能发现（它看起来完全合理）。

### P4. 判读中文页面必须显式 UTF-8 🟡

```
PowerShell Get-Content 默认按 GBK 解码 → 「容量」变成「瀹归噺」→ grep 全不中
```
第一版探针因此误判「苹果 HTML 里没有中文规格」。**这是编码假象，不是数据缺失。**

### P5. 并列值不取平均 🟡

官网写「标准版 234g / 典藏版 235g」。取234（第一个）并在 note 里说明；
**平均 234.5 是编造**——官网从来没这么说过。

### P6. 对象型字段的 provenance 要同时登记父路径与子路径 🟡

`display.resolutionPx` 是 `{w,h}` 对象。曾经规范化层登记子路径 `.w`、
而校验层查父路径 —— 于是 **当时 60 台全部**报「缺 provenance」假警。

**教训：闸门自己也会误报，所以它需要被测**（见 `selftest.mjs` 的对应断言）。
如果闸门失败看起来像「数据本来就缺」，很容易被当成结构性缺口忽略掉。

### P7. 闸门被注释里的「正确值示例」骗过 🔴 **闸门自身失效**

写 `check-conventions.mjs` 时要检查「`base` 必须是 `'./'`」，
但 `vite.config.ts` 里 `base` 上方本来就有一行说明注释：

```ts
// base: './' 是发布到 B 站 Toy 的硬要求 —— 绝对路径资源会 404 白屏。
export default defineConfig({ base: '/' })   // ← 真的坏了
```

正则 `/base\s*:\s*['"]\.\/['"]/` **匹配到的是那行注释**，
于是检查永远通过 —— 闸门在最该拦的地方完全失效，且**零报错**。

**修法**：匹配前先剥掉行注释（`stripLineComments`）。
**判据**：写任何"检查配置/代码文本"的闸门时，
**必须先把注释与字符串排除**，否则示例会变成通行证。

**为什么这条特别危险**：它是**静默失效**——闸门显示绿灯，实际不设防。
比误报（吵你）危险得多，因为你会开始信任它。

**与 P6 的区别**：P6 是闸门**太吵**（误报），P7 是闸门**太静**（漏报）。
两者都源于同一件事：闸门自己没被测。**闸门必须被反向测**：
故意注入违规 → 必须报出 → 改回 → 必须恢复绿灯。

### P8. 字体缺字形是**静默**的：同一句话里有些字像素、有些字圆滑 🔴

站点原带的 `pixel-zh.woff2` 只覆盖项目实需汉字的 **45%**（478/1059）。
浏览器遇到字体里没有的字形会**自动回退到系统字体**，不报错、不警告、照常渲染 ——
于是同一段文字里，命中字形的是像素字，没命中的是圆滑的黑体。
肉眼看是「风格没统一」，代码里所有检查都是绿的：
`getComputedStyle(el).fontFamily` 明明写着像素字体名。

**这类缺口的唯一可靠判据是读字体的 cmap**。浏览器端两条路都走不通，
两次都是闸门自身失效：

| 尝试 | 结果 | 为什么 |
|---|---|---|
| canvas `measureText` 比宽度 | ❌ 恒等，误报 124/124 | 汉字在多数字体里都是全角等宽 1em，两边宽度永远相同 |
| canvas 像素比对，对照组写「不存在的字体名 + monospace」 | ❌ **永远报绿** | 字体名不存在 → 整条 `font-family` 解析失败走系统默认字体；而 SpecPixel 缺字时回退到**列表里的 monospace**。两者本就不同 |
| 同上，对照组改成「单独 monospace」 | ⚠️ 也不准 | canvas 的字体匹配不查 `@font-face` 的 cmap |
| **生成期落 `coverage.json`（码位 + 字体 sha256），闸门只做比对** | ✅ | 权威数据在生成期一次算清；闸门零依赖，CI 只装 Node 也能跑 |

**修法**：`scripts/font/build-subset.py` 生成字体时顺手落
`public/fonts/coverage.json`（含 `fontSha256`），闸门
`scripts/publish/check-font-coverage.mjs` 做两件事：
① 校验 sha256 与磁盘字体一致（防「换了字体忘重生成清单」，那种情况闸门会拿旧数据报绿）
② 用码位集合与「源码 + 数据」求差集。

**判据**：任何「检查样式/渲染结果」的闸门，量法必须先证明有效（sanity check）
**再**用来下结论；且必须反向测两次不同失败路径 ——
本条实测反向测：① 注入真实缺口且清单同步 → 报红 648 字；
② 换字体不换清单 → 报「不同源」。两条都守住才算数。

**顺带一条通用纪律**：字体子集缺的那些符号（`√ ≤ ≥ ⚠ ✓ ✗`）不要写进界面。
本项目的做法是 `src/components/PxIcon.vue` 用 16×16 整数坐标的 SVG 方块路径画图标，
一个像素都不交给字体渲染 —— 图标本就不该由字体提供。

### P9. 手写二进制解析器：woff2 表 tag 是**索引**不是 ASCII 🔴

为省掉「生成期落清单」这一步，试过让 Node 直接解析 woff2 找 cmap。
读出来的 tag 全是乱码（`¸\n)` 之类），最后报「没有 cmap 表」，零报错。

两个错：
1. **表 tag 在 WOFF2 目录项里是「预定义表索引」（0-62），不是 4 字节 ASCII**，
   只有索引 63 才是自定义 tag（后跟 255UInt16 标签）。
2. 目录项 flags 的 **bits 0-5 才是索引**，当时写成 `flags & 0x3b` 把变换相关的位
   混进掩码 → 几乎每张表都判「有 transform」→ 整体错位 → tag 全乱。

**结论**：权威判据放在**能真正读到数据的地方**（生成期的 fontTools），
闸门只做比对。手写二进制解析器省的那点代码，换来的是一个
「不报错但结论全错」的新坑 —— 与 P7 同类。

### P10. 判据要落在「语义不可再分」的最小单位上 🟡

给折叠屏写判据时，正则写成 `/折叠态|展开态|三屏态/`（照着 Mate XT 的官网措辞抄的）。
构建通过、页面正常渲染，**漏判了两台**：

| 机型 | 官网原文 | 第一版判据 |
|---|---|---|
| Mate XT 2 | `折叠态：12.3 mm` | ✅ 命中 |
| Mate X6 | `折叠：73.78 mm \| 展开：144.04 mm` | ❌ **漏**（没有「态」字） |
| Mate X7 | `折叠：73.8 mm 展开：144.2 mm` | ❌ **漏** |

**同一个品牌的两批页面用了两种措辞**，按一家的一种句式写正则必然漏一半，
而漏判的表现是「那台机器没出现在折叠屏筛选里」—— 零报错。

**教训**：判据应落在语义不可再分的最小单位（这里就是「折叠」「展开」两个字），
而不是某页面的具体句式。**写完判据必须用「同一语义、多种措辞」的样例验一遍**，
只拿一个样本验等于没验（`selftest.mjs` 的「同品牌两种措辞」用例就是这个）。

同源的三个变体：
- 拿 `body.folded` 当判据 → 该字段 当时 60 台**全是 null**，页面照常渲染，折叠屏全灭；
- 拿「厚度 > 10mm」当判据 → 属**估算**，Pura X 展开 7.15mm 会被判错。

### P11. Vue SFC 少了 `<script setup>` 开标签，报错指向完全无关的行 🔴

用编辑器写 `.vue` 时漏了开头的 `<script setup lang="ts">`，构建报：

```
[vite:vue] src/views/CompareView.vue (30:23): Element is missing end tag.
```

**报错行号指向注释里的一行**，因为解析器把整个文件当 HTML 扫，
遇到 `<` 就当成标签起始 —— 于是
`Set<string>` / `NonNullable<...>` / 甚至**注释里写下的 `computed<string[]>`** 全成了「未闭合标签」。

**误导性极强**：第一次据此得出的结论是「Vue 不支持在 SFC 里写泛型」，并顺手把注释改写成
「解析器不剥注释」—— 全错。真因是缺一行开标签。

**排查纪律**：SFC 报 `Element is missing end tag` 且报错行在注释/泛型上时，
**先 `head -c 50 文件名 | od -c` 确认首行是 `<script setup lang="ts">`**，再谈别的。
不要根据报错行号去改那一行。

### P13. grid 子项缺 `minmax(0,1fr)` / `min-width:0`：窄屏横向溢出 122px 🔴

机型库页用 `grid lg:grid-cols-[minmax(0,1fr)_22rem]`（宽屏两栏、窄屏堆叠）。
390px 视口下 `scrollWidth=512`，横向溢出 **122px**，页面整体可左右拖。

**根因**：`minmax(0,1fr)` 只在 `lg:` **断点之后**生效，窄屏走的是单栏 `display:grid`，
而 grid 子项默认 `min-width:auto` —— 会被内容宽度顶开。那一列装的是
「精灵图 + 机型名 + 价格 + 详情按钮」一行，最窄也要 496px，于是整页被撑破。

**修法两处都要**（只改一处仍会在另一个断点破）：
1. 列定义给 `minmax(0,1fr)`（已有）；
2. **子项加 `min-w-0`** —— 这是真正起作用的那一步。

```html
<div class="grid gap-6 lg:grid-cols-[minmax(0,1fr)_22rem]">
  <div class="min-w-0">…</div>   <!-- ← 关键 -->
  <aside class="min-w-0 …">…</aside>
</div>
```

> 与「固定像素 padding 窄屏破功」是**同一族**问题：容器没给出「可收缩的宽度下限」，
> 内容就按自身最优宽度撑破视口。**判断法**：`scrollWidth > clientWidth` 时
> 用 `getBoundingClientRect()` 逐层找出 `width > clientWidth` 的元素，别猜。

### P14. 筛选器的「缺数据」必须可见可点，否则等于静默丢数据 🔴

实测 当时 60 台里 **19 台官网没公布芯片名、30 台没公布内存**。
筛选器最初只列出「有值」的项，结果：筛「芯片 = A19」后，那 19 台**从界面上消失且无处可寻** ——
用户看到的是「怎么少了几台？是不是数据丢了？」，而页面上没有任何地方说明它去哪了。

**规矩**：缺字段是一个**正常取值**，给它一个可点的分面项（标「未公布」），
这样用户能主动把它们全部提出来，也能一眼看到「这批机器官网没给芯片」。

配套三条：
- **分面计数按「其它维度已生效」算，不受自身维度影响**。否则选中「苹果」后
  芯片分面只剩苹果芯片，一点就锁死、没法改主意（`applyExcept` 就是干这个的）；
- **「未公布」永远排最后** —— 它不是一个小数值，混进数字档会被误读成「最小/最大」；
- **缺值不等于 0**：排序时 `null` 排末尾。把缺价当 0，「官方未公布」会被
  渲染成「全站最便宜」。

> **反向测还抓出一个测试缺口**：只测了 `applyFilter` 能筛出「未公布」，
> 没测它能经 **URL 往返**。真去改代码把「未公布」从 `readFilter` 的合法值里排除，
> **一个用例都不报红** —— 症状是「本页能筛出来，但把链接发给别人就筛不出来了」。
> 已补 `「未公布」筛选条件能经 URL 往返` 用例（`selftest.mjs`）。
> **教训：可分享的状态（URL）必须测往返**，只测「算得对」不够。

### P15. 分面的「选项枚举」和「计数」必须分开：枚举看全集，计数看子集 🔴

`facetOf(products, dim, pool)` 最初**枚举和计数都遍历 `pool`**（除自身维度外的筛选子集）。
选了两个华为芯片后，品牌子集里只剩华为 → 苹果从品牌分面**整个蒸发** →
FilterBar 的「选项 >1 才显示维度」把品牌触发器**整个藏掉**，用户没法反悔。
零报错，纯静默。旧的行内布局同样有这 bug，只是没人选到那一步；改下拉式后冒烟
「触发器数量对不上」才暴露。

**规矩**：`pool` 只用来**算计数**（联动口径），**选项枚举必须遍历全集** `products`，
0 计数项照常出现、靠 `count === 0` 灰显禁用 —— 这正是京东/淘宝范式（档位常驻、不兼容灰显）。

**为什么旧测试没拦住**：旧用例锁的恰恰是**错误行为**（「选苹果后芯片分面不该出现麒麟」），
与 P14 的「可反悔」设计自相矛盾 —— 测试把 bug 固化成了契约。
**教训：写分面断言前先问「这个语义和 UI 的承诺一致吗」**；已改为
「0 计数仍出现 + count=0 + 维度不消失」三条断言（含反向测）。

### P16. 同一条判据写两份，用户的标签和自己的图互相打脸 🔴 闸门抓不到

**症状**：机型库把某几台标着「折叠屏」，首页立绘却把它们画成直板砖。
台数没错、数据没错、页面不报错、闸门全绿、像素风扫描全绿。

**根因**：折叠屏判据写了两份，且**都不对**：

| 位置 | 判据 | 结果 |
|---|---|---|
| `src/lib/catalog.ts` | 官网尺寸原文含「折叠/展开」 | 对，7 台 |
| `scripts/sprite/generate.mjs` | `sizeIn >= 7.5 \|\| line 匹配 x\d` | 错，4 台 |

`sizeIn >= 7.5` 漏掉三台真折叠机（Mate XT 2 主屏 6.5″、Pura X 6.3″、Pura X Max 5.4″），
反过来将来 8 英寸平板会被误判成折叠机 —— 这是 P「不用厚度/尺寸阈值」那条坑的变种：
**拿数据反推形态属于估算，而估算在这里是错的。**

**为什么三个防线全部失效**：
- 单测抓不到 —— `layout()` 返回的仍是合法数字，只是画错了；
- 产物闸门抓不到 —— SVG 结构完整、无外链、无模糊；
- 像素风扫描抓不到 —— 圆角/模糊/字号都合规。

**怎么发现的**：新加的 `scripts/sprite/review.mjs`（按**几何特征**分组排立绘，
每台标出几何依据）。折叠档里混进了一台直板机，一眼可见。
**按 id 排序的截图看不出这个 —— 必须按几何分组才看得出「这一类画错了」。**

**修法**：判据下沉到 `scripts/lib/foldable.mjs`（唯一真源，含三个实测坑的说明），
前端与立绘都引它。自测锁住「两者对同一台机器的判断必须一致」+反向测
（把判据改回 `sizeIn>=7.5`，6 条断言同时报出）。

**教训**：
1. **判据与阈值只能有一个真源。** 两处各写一份正则，必然分叉。
2. **新增「视觉由数据算出」的功能时，必须同时出一个按几何分组的审查表。**
   那类改动没有任何自动防线，只有「人看一眼」。
3. 审查表按什么维度分组，决定它有没有用 ——
   按 id 分组只能看「整体像不像」，按几何分组才能看「这一类对不对」。

### P17. curated 数据放进了 `_work/`，等于没有 🔴 已造成全站失效

**症状**：本地一切正常，CI 每一次同步都失败——当时 60 台全部因「无发布日期」被窗口过滤丢掉。

**根因**：`data/release-dates.json` 是人工核对的取证表，却曾躺在 `_work/` 下，
而 `_work/` 在 `.gitignore` 里。CI 全新 checkout 拿不到这张表。

**为什么这类错误容易复发**：`_work/` 在直觉上就是「数据目录」，
把人工维护的文件放进去看起来很自然。同一类里还有一个：
`data/discovery-pending.json`（待收录队列）曾经也只写进 `_work/sync-report.json`。

**纪律**：`data/` 下分两类，**都不许进 `_work/`**——
- 运行产物：`products.json`、`raw/`（由取数生成，可复现）
- **curated 数据**：`release-dates.json`（人工取证）、`discovery-pending.json`（等人工补的队列）
  ——后者由运行产生但**必须入库**，因为它是「可行动清单」，丢了就等于没有。

### P18. 新加的入库文件没接进 CI 触发条件，等于没做 🔴

**症状**：`data/discovery-pending.json` 正确写盘了，但新机发布后它永远提交不进仓库。

**根因**：CI 的提交条件只看 `data_changed` / `site_changed` 两个指纹。
而队列变化时**两个指纹都不动** —— 缺发布日期的机器进不了 `products.json`，
台数没变、页面没变，于是「这一步压根不跑」。
最隐蔽的地方在于：**它是完全静默的**，台数没少、页面没变、零报错。

**修法**：给队列与归档各自单算一个指纹（`pending_changed` / `raw_changed`），
加进 `if:` 条件；并且**不参与站点指纹** —— 队列变化不该触发重新发布站点。

**纪律**：新增入库文件时问一句「它变了但 `products.json` 没变时，怎么让它进仓库」。
这一条与 P3（闸门挡不住少取值）、P7（闸门被注释骗过）同源：
**失败发生在没人看的那条分支上。**

### P19. 扫描脚本的「页面清单」是白名单：新页面不在清单里 = 没被扫 🔴

**症状**：`#/about` 页长期带着两处违规字号（`text-[14px]` 与 `text-[32px]`），
而 `_smoke-pixel.cjs` 每次跑都是「✅ 零违规」。

**根因**：脚本里的 `PAGES` 是**硬编码白名单**，只有 9 个路由。
关于页不在里面 → puppeteer 根本没打开过它 → 扫描全绿。
**闸门输出的是「清单内那几页没问题」，措辞却是「零违规」。**

**修法**：把 `['about', '#/about']` 加进 `PAGES`，当场报出 4 处 `14px`。
改成 12 的整数倍后复跑，全绿。

**纪律**：与 P18 同源 —— **闸门的覆盖面本身也是要维护的契约**。
加页面时问一句「它在这个脚本的清单里吗」。
清单型白名单的通病：清单是历史遗留的，**没人会主动往上加东西**。

### P20. 产物闸门的「零外链」只覆盖 HTML/CSS，JS chunk 不在扫描范围 🔴

**症状**：在 Vue 组件里写了站外链接（`href="https://github.com/..."`），
`verify-dist.mjs` 报「外部 0 · 零外链 ✅」，但 `grep` 产物能查到那个域名。

**根因**：`scanTargets` 只含 `.html` 与 `.css`。
Vue 模板里的 `href` 编译后进的是 `dist/assets/*.js` chunk —— **压根没被扫**。

**这不算误报，但要读懂它在说什么**：该闸门防的是
「外链**资源**」（CDN 字体/脚本/图片），那是 Toy 包内自包含的硬要求；
超链是**用户点击后才发生的导航**，不在其职责内。
报告里的「零外链」应理解为「零外链资源」。

**纪律**：不要因为「闸门说零外链」就认为产物里没有外链字符串。
反过来也别把超链当资源引进来 —— 引用资源一律走 `asset()` 走相对路径。

### P21. 把低频页移出导航 → 它变成了孤儿页 🔴 零报错

**症状**：某页有路由、能打开、内容也完整，但**没有任何导航链接能到达它**。
搜索引擎能进来，用户走不进来。冒烟脚本全绿（它测的是「已知入口还能用」）。

**场景**：2026-10-06 精简顶栏，把「关于」从主导航移到页脚（它访问频率最低，
不该占主导航的视觉预算）。搬的时候页脚确实加了入口，但**没有任何断言守着这一条** ——
下次有人觉得「页脚太乱」把它删掉，就静默变成孤儿页，而那种删除看起来只是「清理」。

**为什么难发现**：
- 页面能打开 → 功能测试全过；
- 路由存在 → 构建不报错；
- 冒烟脚本只测「已知入口还能用」，**不测「有没有漏掉的入口」**。

**修法**：自测里加一组**路由可达性**断言（扫 `src/**/*.vue` 的 `to=` 与路由表求差集），
另加一条钉住页脚必须保留「关于」入口。
**反向测**：删掉页脚那行 → 断言报出。

> 写这条断言时自己踩了一次：判据只认模板字面量 `to="/about"`，
> 而页脚是**数据驱动**渲染的（`{ name:'about', to:'/about' }`）→ **误报**。
> 判据要认两种写法。这与 P7（闸门被注释里的示例骗过）同源：
> **判据写窄了，它会把正确实现误判成故障**，比漏报更难排查——
> 因为你会去「修」一个没坏的东西。

**纪律**：移入口 ≠ 删入口。**任何「从 A 处挪到 B 处」的改动，都要问一句
「B 处的入口有没有断言守着」**——这与 P18 同源：
**失败发生在「看起来只是整理」的那条分支上。**

### P22. 一组判据可能整体漏掉一整类故障（favicon 五条判据全都镜像不变） 🔴 零报错

**症状**：把 `public/favicon.svg` **整幅左右镜像**，`selftest` 依然 **223 项全绿**。

**为什么**：原有 5 条 favicon 判据——两色 / 深色占比 / 180° 旋转后黑白互换 / 圆环闭合 / 无鱼眼——
**逐条看都合理，但它们全都是镜像不变的**：

| 判据 | 为什么镜像不变 |
|---|---|
| 深色占比 | 镜像不改变格子数 |
| 圆环闭合 | 镜像把环映射到环|
| 180° 旋转后黑白互换 | **过中心的反射与 180° 旋转可交换** ⇒ 镜像后仍满足 |
| 有无鱼眼 | 位置无关|
| 只能是 theme 两色 | 与图形无关 |

**这不是某条判据写坏了，是「判据集」少了整整一个自由度。**
根因是推导时只列了「需要检查的性质」，没问「**这些性质 collectively 能区分多少种可能的图**」。

**修法**：先找图形已声明的对称性（本例：180° 旋转 + 换色不变），
它把候选图形压到只剩 **{本身, 镜像}** 两种 ⇒ **一个比特就能钉死**。
本项目取的那一位是**最易读、也最难被边界噪声翻转**的：
**赤道带内白鱼（浅色）面积的重心落在圆心哪一侧**。
期望方向不是目测 —— 由源path 的赤道交点 x=541.5 经镜像 ⇒ 482.5 推出。

**反向测**：`scripts/verify-favicon-gates.mjs` 注入「整幅左右镜像」⇒ 必须命中手性判据。

**纪律**：加一组判据时，问一次「**把产物做哪些等价变换，它还能过？**」
（镜像 / 旋转 / 平移 / 换色 / 缩放）。**过得了的变换就是盲区。**

### P23. 从 SVG 反推几何时漏掉 `<g transform>` ⇒ 整幅镜像 🔴 判据「有失败」但方向错

**症状**：`scripts/verify-favicon-gates.mjs` 逐格对拍报 **212 格（20.7%）不符**，
分类 `{漏黑: 106, 漏白: 106}`。

**为什么**：`数学完美太极_逆版.svg` 把circle / rect / path **全部**包在
`<g transform="matrix(-1 0 0 1 1024.0 0)">` 里 —— 以 x=512 为轴的**水平镜像**。
渲染器自动处理，所以**出图管线完全正常**；而解析式实现直接读 `d="..."` 的原始坐标
当最终坐标 ⇒ 拿到的「理想太极」是镜像的。

**为什么难发现**：
- 「完全对称的不符」正是镜像的指纹 —— 真正的采样口径差（BOX 平均 vs 点采样）
  会**零散地**分布，不会 106/106 这么整齐。**分类计数对称就该往变换上想。**
- 两张图肉眼看**完全一样**（太极本来就是中心对称图形）。
- 先后怀疑过三次口径：映射比例写反、`idealCell` 漏判 `null`、面积投票 vs 单点采样。

**修法**：`composedMatrix()` **解析并合成**文件里出现的全部 `matrix(...)`（按文档顺序），
而不是硬编码这一条 —— 源文件换了变换不能又悄悄错回镜像。
注意圆弧要在**路径自身坐标系**里展开、最后再整体过变换（顺序反了弧会错）。

**副产物**：镜像不改变环绕方向，非零环绕只看 `!== 0` ⇒ `insidePolygon` 不受影响。

**纪律**：**凡从 SVG/图形文件反推几何，必须把变换链走完再当结论。**
「渲染器会处理」不等于「不需要你知道它做了什么」。

### P24. 反向测脚本自己会有 bug —— 注入失效被误读成闸门失效 🔴 返工两轮

**症状**：`scripts/verify-favicon-gates.mjs` 报「❌ 这类故障无闸门覆盖」，
但闸门其实没问题，是**注入没生效**。两次：

1. `s.replace(/\s*shape-rendering="crispEdges"/, '')` ——
   产物顶部说明注释里**也写了** `shape-rendering="crispEdges"` 字面量（P7 同源），
   裸`replace` 先命中注释；而判据又剥注释 ⇒ **注入「看起来生效了」而产物实际没变**。
2. 「挖一个鱼眼」那条用「四邻是墨」挑格子，挑中了**圆环上**的格子 ——
   环只有 1–2 格厚，斜角就通到外部纸区，根本形不成洞。
   改判据时才发现：**分块连通性必须与「洞」的定义配套**
   （4-连通 vs 8-连通，见 `selftest.mjs` 的鱼眼判据）。

**修法**：
- 注入只改**剥注释后的正文**或精确定位到 `<svg>` 标签；
- 通用注入helper：解析网格 → 改 → 重排 run 写回，别按坐标 `replace` 某个 rect
  （产物按 run 合并，同一行有多个 rect，正则会命中该行的**第一个**）；
- **注入后自查「文本真的变了」**，并把「注入无效」与「闸门失效」分成两种报错；
- 崩溃安全：先写 `_work/favicon/favicon.bak`，启动时若发现备份残留就先还原 ——
  否则进程被 kill 会把**被 git 跟踪的**产物留在损坏状态，下次提交就进去了。

**纪律**：**反向测通过 = 闸门能拦住；反向测失败 = 不知道是谁坏了。**
先证明注入有效，再谈闸门结论。

### P25. 判据会过期 —— 过期时改判据，不是逼需求迁就判据 🟡 会误报，危害排在真 bug 之后

**症状**：顶栏灰阶断言「相邻两档亮度差 ≥ 3%」在 16 档方案下失败，实测相邻差只剩 1.1%。

**当时的诱惑**：把阈值从 3% 调到 1%，让它绿。

**为什么不能这么干**：这条判据表达的是「**档与档要分得开**」。
3% 是 6 档时代定的数值，**不是这个性质本身**。需求从 6 档变 16 档后
「相邻差 ≥3%」**失败得有道理** —— 它确实降到了 1.1%。
继续钉 3% 等于把「档数更密」这个明确的用户需求判死。

**修法**：改落到**与技术手段无关的量**上 ——
「相邻档必须跳 ≥2 级 8-bit 灰阶」。它在6 档和 16 档下都成立。

**同源的演进**（顶栏高度）：钉「第一档必须是 80px」→ 改成钉**死空间对称**
`档高 − 实测内容 ∈ [8,12]`。后者抓的是「有没有死空间」这一类错，不是某一个值；
写完第一次跑就抓出**我自己漏改的一档**（base 档还是 124）。

**纪律**：判据分两类 ——
**结构性判据**（「必须分得开」「不能有死空间」，可跨方案成立）与**数值判据**（「必须是 80px」，
与某个方案绑定）。**需求变了先问：这条判据表达的是性质还是数字？**
是数字就随方案更新；是性质却失效了，才是需求出问题。

### P26. 改写产物的脚本与读产物的脚本并行 ⇒ **谎报**，不是报错 🔴 零报错

**症状**：`favicon:diff` 报「源去掉 `<g transform>` ⇒ 抓到 **0 格**」，
而这条用例**单独跑必过**（实测 212 格）。同一时刻 `favicon:gates` 报 7/7 全绿。
两条命令**各自单跑都对**，只有并行时有一条出错。

**根因**：`verify-favicon-gates.mjs` 为了反向测，必须**原地改写**
`public/favicon.svg`（这是它的工作方式）。而 `verify-favicon.mjs` 同时在读它
⇒ 读到**中间态**。七条注入里正好有一条是「整体左右镜像」，于是那一刻磁盘上的产物
**就是镜像版**；而本用例注入的是「源去矩阵」（= 未镜像）⇒ 未镜像 vs 镜像本该212 格，
却读到镜像版 ⇒ 0 格。

**为什么这条最阴**：三个条件同时成立才触发 ——
① 一个脚本**原地改**共享产物；② 另一个脚本**并发读**它；
③ 两者在时间上**恰好重叠**。人不会去并行跑两个「看起来互不相干」的检查命令，
所以**复现一次就以为是自己手抖**，再跑一次单跑全绿，就把这条真缺陷放过了。

**修法（两步，缺一不可）**：
1. **锁**：`scripts/lib/gates-lock.mjs`。写方`tryLock()`（`wx` 标志天然原子），
   读方 `assertUnlocked()` 见到锁就**退出码 2 响亮失败** —— 绝不降级成 warning 继续跑。
2. **子进程旁路**（容易漏）：反向测自己会**反复 spawn selftest**。
   若selftest 也无条件查锁 ⇒ 七条注入**全被自己的锁挡住**、全误判成「闸门失效」，
   比原来的谎报更糟。故持锁方 spawn 时传`FAV_GATES_CHILD=1`，`assertUnlocked` 据此跳过。

**顺带写下的顺序纪律**：**先拿锁，再查备份残留**。
若顺序反了，第二个 gates 会把「第一个 gates **正在写**的备份」当成「上次崩溃的残留」还原掉
—— 那是**进行中的注入**不是垃圾，还原它等于搅黄对方的实验，而两边都还报绿灯。
（备份文件本身就是「有人正在跑」的证据，与锁文件同义。）

**另一条同源纪律**：`catch` 比 `finally` **先**执行。
所以「基线失败」这类分支**不能在 `catch` 里`process.exit()`**（会跳过 `finally`，
锁与备份双双残留）—— 只能置标志，退出码留到块外给。

**通用教训**：`try/finally` 只保证**本进程**的清理，不保证**别人读到的**一致性。
凡是「A 改 / B 读同一文件」的组合，B 的正确性就依赖一个**跨进程**的互斥，
而不是进程内的 `finally`。判断依据：被改的文件**是不是 git 跟踪的产物**。

**附带的次级教训**：用 `&` 把命令丢后台时，**shell 的 cwd 会变**——
`node ./scripts/x.mjs` 在后台子进程里解析成了 `dsh/scripts/x.mjs`（MODULE_NOT_FOUND）。
「并发测试脚本本身没跑起来」看起来和「并发导致失败」一模一样，
所以并发类验证必须**先确认每个进程真的跑起来了**（看退出码 + 看输出），别只看最终结论。

### P27. 「文件存在且被跟踪」≠「浏览器能渲染」—— 正则层校验对 XML 合法性完全失明 🔴 零报错

**症状**：用户报「标签页图标还是之前的，不是现在这个修改后的太极」。
排查到底层发现 **两件独立的事**：

| # | 事实 | 性质 |
|---|---|---|
| 1 | `public/favicon.svg` 是 **untracked**，`git log` 零提交，线上 `GET` 返回 **404** | 发布没做 |
| 2 | 但**即使推上去也不对**：那个 SVG 是**非法 XML**，浏览器直接拒绝渲染 | 产物本身是坏的 |

第2 条才是「一直显示旧图标」的真正原因 —— 浏览器拿到一份解析失败的文件，
只能退回缓存里的旧版本，于是**看起来像缓存问题**，实则是文件根本无效。

**根因**：XML 规范规定**注释体内不得出现连续两个减号**。这份 SVG 的头部说明注释里
有两处踩雷：① Markdown 表格分隔线；② 注释里写命令行 `--flag`。
⇒ 整个 SVG 成了非法 XML。

**为什么所有闸门都绿**（这是本条最值得记的部分）：

| 已有判据 | 为何漏 |
|---|---|
| 网格 / 深色占比 | 正则按 `<rect>` 取几何，**不关心 XML 是否合法** |
| 颜色语义 / `crispEdges` / `width` | 同上，各自只看自己那一项|
| `favicon:diff` 逐格对拍 | 只按 `<rect>` 解析出网格，**绕过 XML 解析器** |
| `favicon:gates` 反向测 | 注入的都是**合法 XML 的坏图形**（错色、断环、镜像） |

⇒ **每项单看都「有内容」，合起来全绿，而产物一个像素都显示不出来。**
严重性与量级无关：不���某格错，而是**整个资源不存在**。

**修法**：把合法性做成判据本体
- `selftest.mjs` 新增「必须是合法 XML」：扫每段注释里有无连续减号 + 确认注释都正常闭合；
- `favicon:gates` 新增第 8 条反向测注入（往注释里塞表格分隔线），确认判据**能拦住**；
- 产物注释新增第〇节，把这个坑和「写法替代方案」写在元凶所在处。

**更值钱的三条通用结论**：

1. **解析器层面的校验有天然盲区**：只要判据是「正则 + 字段抽取」，
   它就永远测不到「文件能不能被真正的解析器读进去」。
   ⇒ **产物类资源必须有一道「交给真解析器过一遍」的判据**，
   或至少一道**真实消费者过一遍**的验证（这里是浏览器栅格化）。
2. **「能解析 ≠ 能显示」是独立的一维**，不能因为解析成功就认为显示正常。
   本仓已有的同类教训是「只有 `viewBox` 无 `width/height` ⇒ 渲染成纯黑方块」，
   那次也是「文件合法、DOM 在、闸门全绿、显示是错的」。
3. ⚠️ **连写「反面教材」都会踩这个坑**：本条文档第一版为了说明问题，
   **把 `--` 示例本身写进了注释**，selftest 当场报非法 ——
   改完还得再改一遍。故这条**只能靠自动判据守，不能靠写文档时的自觉**。

**排查决策树补一条**：
用户报「改了 X 但没生效」⇒ 先分清三类，**别直接归因缓存**：
①产物没发布（查 `git status` + 线上 `curl -I` 看状态码）；
② 产物本身无效（**交给真解析器/真消费者试一次**）；
③ 真的是缓存（①②都过了才轮到它；此时给链接加版本指纹）。

### P28. 索引层级混淆：`c@s` 是 `cellXfs` 下标，不是 `fills` 下标 🔴零报错，症状像"设计意图"

**症状**：从 WPS 导出的 xlsx 里读两色网格，读出来**黑白整体判反** ——
太极的手性与参考图相反。看起来像"设计师做了个镜像版本"，于是被当成设计意图接受下来。

**根因**：xlsx 的样式是**两层间接**，我少走了一层：

```
单元格 c@s──→  cellXfs[s].fillId  ──→  fills[fillId].patternFill/fgColor
```

把`s` 直接当 `fillId` 用，会读到**另一条 fill**。本项目数据：

| 下标 | cellXfs entry | → fillId | → 实际颜色 |
|---|---|---|---|
| 0 | `fillId="0"` | 0 | `<patternFill/>`（**无填充**） |
| 1 | `fillId="2"` | 2 | `solid fgColor=FFFFFFFF`（白） |
| 2 | `fillId="3"` | 3 | `solid fgColor=FF000000`（**黑**） |

误用 `fills[s]` 时，`s=2` 被读成 `fills[2]`=**白**，而它真实是 `fills[3]`=**黑** ⇒ 正好判反。

**为什么难发现**：网格**看上去完全正常** —— 每行都有黑白、比例仍是精确的 512:512。
错的只有"哪个是哪个"，也就是**语义**而非**结构**。
这类错误天然躲过所有结构性判据（连通块、旋转对称、占比），只被一条语义判据抓住。

**修法**：`load_styles()` 返回 `(fills, cellxfs)` 两张表，`load_sheet()` 按
`fills[cellxfs[s]]` 三级解析。另加一条守卫：`fillId` 越界时显式报错，
不许默默降级成"无填充"。

**三条通用结论**：

1. **"读出来的东西有形状"不等于"读对了"**。本次若只看「两色各512 格」这个统计，
   会认为数据完美 —— 黑白颠倒**不改变任何频次**。
2. **按频次定语义在这里必然失效**：无填充与实心填充恰好各 512 格（512:512），
   频次完全相同 ⇒ 任何"取多数当前景"的写法都会在两个版本间随机翻转。
   ⇒ **两色图判语义只能用亮度**。
3. ⚠️ **同一段解析里还藏着一个 off-by-one**：xlsx 行号是 **1 基**（`A1` 的那个 1），
   而列号通常转成 0 基。少减这一个 1 ⇒ 网格整体下移一行：
   **顶部多一行空、底部少一行**，看起来像"构图本来如此"。
   ⇒ **同一份数据里不要混用两种基**。

### P29. 换构图时，判据与注入必须**同步退役**，不能留空壳 🔴 会误报，危害排在真 bug 之后

**症状**：用户裁决"完全照参考图"，favicon 从「米白底 + 墨环 + 无鱼眼 + 圆占 80%」
换成「纯黑白 + 满幅 45° 斜分 + 两只鱼眼」。产物换完后：

| 判据 | 状态 | 后果 |
|---|---|---|
| 「只能是 theme 的ink/parchment」 | **恒失败** | 正确产物被判错 |
| 「深色占比 ≈ π/4·frac²·0.5 + π·frac/n」 | **恒失败** | 公式里的 `frac` 项来自圆环周长，新构图没有环 |
| 「圆环必须闭合」（从边缘 flood-fill 浅色） | **恒真** | 满幅构图下浅色格全部与边缘连通，这条**永远绿** |
| 「鱼眼已被移除」 | **恒失败** | 用户明确要鱼眼回来 |
| 「赤道带白鱼重心在左」 | **恒失败** | 斜分背景穿过赤道带，把重心拉偏（实测 +7.5） |

**五条里有四条坏掉** —— 而 `npm run selftest` 只是"红"，看不出是哪条判据的**设计**错了。

**最容易漏的是"恒真"那条**：圆环闭合判据在新产物上永远通过，
看起来"判据还在守着"，实则它描述的是**早已不存在的性质**。
只有问「产物做哪些变换/改动它还能过？过得了的就是盲区」（P22）才会暴露。

**修法**（本次的纪律）：

1. **判据的期望值必须从构图参数推出，不能钉死常数**，也不能沿用旧构案的公式。
   新的占比期望是`0.5`，推导来自「45° 斜分恰好平分画幅 + 太极自身黑白各半」——
   **与圆的大小无关**，所以它对「斜分角度偏」「太极填反」「圆缩小」三类故障都敏感。
2. **换构图时作用域往往能变简单**：旧版要"圆内、排除 1px 环"，
   新版满幅斜分背景本身就满足 180° 旋转换色 ⇒ **全图 1024 格都该成立**
   （实测 0 不符），覆盖面从 616 格扩到 1024 格。
3. **手性锚点要选"与新背景无关"的那个**：赤道带重心被斜分污染 ⇒ 改用**鱼眼重心**
   （鱼眼位置由太极几何唯一确定）。同时把变量名从 `white`/`black` 改成
   `eyeOnWhiteFish`/`eyeOnBlackFish` —— 见下条。
4. **反向测的注入必须同步换**。旧注入（挖环、删鱼眼、改底板色）在新产物上
   要么文本不变、要么命中错对象。本次重写后 9 条里有 3 条第一版是坏的。

**一条元教训**：`const white = eyes.find((e) => !e.t)` 这行里，
`white` 到底是"白色的眼"还是"白鱼的眼"？太极的两只眼分属两条鱼：
**白鱼的眼睛是黑色块，黑鱼的眼睛是白色块**。我按"白色的眼"判方向 ⇒ 期望钉反 ⇒
正确产物报失败。⇒ **变量名要带"所属对象"而不只是属性**（`eyeOnWhiteFish`），
这是"同名不同义"唯一可靠的防法。

### P30. 反向测的注入必须制造**真故障**，不能制造"看起来像故障的东西" 🔴 测的是反向的东西

**症状**：XML 合法性判据（见 P27）在反向测里报「selftest 仍全绿 ⇒ 无闸门覆盖」。

**根因**：我注入的是 `|  =  |` —— 而那**正是产物注释里推荐的安全写法**
（`--` 要写成 `= `）。注入让文本变了（所以"注入有效性自查"通过了），
但 XML 仍然合法 ⇒ 判据正确地全绿 ⇒ 我却把结论写成"闸门失效"。

⇒ **"注入生效"与"注入制造了故障"是两件事**，只查前者会得出完全反向的结论。

**同一处还连续废掉两次**（同一个病：注入锚点靠人工同步）：

| 版本 | 锚点 | 为什么废 |
|---|---|---|
| ① | `## 一、` | 米白构图时期的头部注释，换构图后已退役 |
| ② | `构图：满幅` | 产物里实际写的是 `favicon：满幅`（我又凭记忆改的） |

两次都报"注入无效（文本没变）"，读起来完全像闸门的锅。
⇒ **锚点要从产物里现取**（`s.match(/<!--
([^
]*)/)?.[1]`），
改注释永远不会让它静默失效。

**两条通用结论**：

1. **反向测必须双向自查**：「注入是否改变了文本」+「注入是否引入了目标故障」。
   只做前者时，你测的是"闸门会不会误报"，不是"闸门能不能拦住"。
2. **`must` 允许是数组**。改构图类注入常引发**连锁失败**——
   本次填掉一只鱼眼同时破坏了旋转对称、手性、连通块三条判据，这是**正确**行为；
   若只认一条具名判据，就会把"闸门抓到了"误判成"闸门抓错了"。

### P31. 「参考文件」与「真源文件」可能是**不同的构图** 🔴 零报错

**症状**：为了核对 xlsx 网格，把同名的参考 PNG 降采样到 32×32 与之对拍，
**最少也有 352/1024 格不符**（遍历 4 个 xlsx × 4 个 PNG × 8 种二面体变换，全不匹配）。

**根因**：它们**同源不同构图**。程序化量出来的：

| 文件 | 太极直径 / 画幅 | 背景 |
|---|---|---|
| `数学完美太极_逆版45.png` | 465/1400 = **33%** | 45° 斜分 |
| 同一 xlsx 的 `512x512` sheet | **100%**（满幅外切） | 45° 斜分 |

⇒ 拿 PNG 的降采样当"标准答案"去判xlsx 的对错，**判据本身是错的**。

**顺带暴露的真源判据**：该xlsx 里有 10 个 sheet（32/64/128/256/512 × 可见/数据）。
内容一致（512 降采样到 32 与 32 表**逐格相同**，实测 0/1024 不符），
所以取哪个都对 —— 但**32 表是抽稀、512 表才是设计师面对的真实画布**，
记录几何参数时要说清用的是哪一份。

**三条通用结论**：

1. **"文件名相同"不等于"内容相同"**。本项目早就有同名的 `.png` 与 `.svg`
   不是一份设计（P见MEMORY）；这次是 `.png` 与 `.xlsx` 也不是一份构图。
   ⇒ 引用参考文件前先**程序化量一遍**（尺寸/占比/主色分布），别靠文件名与印象。
2. **降采样不等于原图**。BOX 降采样 1400→32 会把斜边平均糊掉，
   拿它当"真源对照"会把正常的作品判成错的。
   ⇒ 像素级作品**必须从逐格数据（xlsx / 像素矩阵）取，不从渲染图降采样取**。
3. **"全都不匹配"本身就是信号**。若穷举变换后最小失配仍很高，
   该怀疑的不是变换找错了，而是**两个源根本不是同一张图**。

### P32. 闸门的**白名单越宽，闸门越像装饰品** —— 它放过的正是要抓的 🔴 零报错

**症状**：i18n 全量抽取做完，`npm run smoke:i18n` 26 次渲染全绿，
全站看起来已经是双语的。深扫时发现英文页上还挂着三处中文：
画布分面的「全部」、搜索提示里夹在两个 `t()` 中间的「与」、参数表的芯片名「麒麟」。

**根因**：冒烟判定「英文页有没有残留中文」时用了数据白名单，
而白名单是把 `public/data/*.json` **全文**扫一遍抽 CJK 连续段得来的（946 段）。
`products.json` 里的 `rawOfficial`（官网原文，中文成段）把「全部 / 与 / 麒麟」
这类常用字全变成了白名单词 —— 于是真漏网的硬编码被自己家的白名单放过了。

**为什么是最难发现的一类**：白名单的目的是降噪，而降噪**看起来是成功的**
（第一版从几百条假警降到 0 条）。误报消失会让人开始信任闸门，
此时漏报比误报危险得多：误报只是吵，漏报让绿灯变成谎言。

**修法**：白名单只认两级，且**把标识与描述分开**：

| 级别 | 来源 | 理由 |
|---|---|---|
| 产品标识 | `name` / `nameZh` / `line` / `modelCode` / 品牌名 | 机型名本来就叫那个名字 |
| 官网原文值 | `specs` 里的值（**`chipset.name` 除外**） | 从中文官网抓下来的原文 |
| ❌ 不再是白名单 | `rawOfficial` 全文 | 中文成段，什么词都能洗白 |

`chipset.name` 单独拎出来不许进白名单：芯片型号有厂商公布的官方英文名
（麒麟 = Kirin），它是**标识**不是**描述**，必须翻译。
收窄后白名单从 946 段降到 124 段，三处漏网立刻报红。

**两条通用结论**：

1. **白名单的每一个来源都要能说出「为什么它里面的词不算故障」**，
   说不出就是在给未来的漏报铺路；
2. **改完闸门要反向测「当初漏掉的那一种」**，不是测「注入一个明显的错」——
   本轮把「全部」改回硬编码做反向测，才发现它根本不在 SSR 渲染范围内
   （那是另一个问题：`Facet.label` 是死字段，两个页面都自己算展示名）。

### P33. 白名单不能拿「原文」当依据，要拿**同一函数算出的结果** 🔴 零报错

**症状**：P32 收窄白名单后冒烟立刻抓出三处真漏网，修完又绿了。
但隔一轮发现：「芯片」二字在 `/compare` `/rankings` `/search` 上残留，
而白名单是从 `public/data` 的 specs **原文**抽的 —— 原文里有「芯片」，
所以它被当成「数据自带的中文」洗白了，尽管页面显示的那个值**已经能翻译**。

**根因**：白名单和翻译逻辑是**两个各自演化的东西**。
翻译能力提升了（`glossary.json` 新增 `A18 芯片 → A18 chip`），
白名单却还停在「按原文放行」的旧口径上，于是它放行的范围**比实际需要的更宽**。
P32 修的是「白名单太宽」，这次是同一种病换了件衣服：**白名单没有跟着真源走**。

**修法**：白名单不许自己判「这个词算不算数据」，必须**调用被测系统的同一个函数**：

```js
// scripts/smoke/i18n-ssr.mjs
for (const m of localizeSpecValue(v).matchAll(CJK_RUN)) out.add(m[0]);
//                 ↑ 先过术语表，只收「翻译完还是中文」的
```

这样白名单自动跟随词表收窄：补一条词，白名单瘦一圈，闸门紧一分。
收窄后 124 段 → 89 段，并立刻抓出「芯片」残留，
顺带暴露两处**直读原值、没走统一出口**的展示点（`search.ts` 的建议词、
`CanvasView` 的短规格行——它们绕过了 `chipNameLabel`）。

**通用结论**：

1. **白名单/豁免/基线这类「降噪配置」必须与它要豁免的那个机制同源**，
   手工维护的豁免清单一定会漂 —— 机制前进了，清单还站在原地替故障打掩护；
2. 同一份展示值在 N 处被读取时，**必须有且只有一个出口函数**。
   「参数表走翻译、搜索建议直读原值」这种分叉，只有靠「白名单跟着真源走」
   之后才会被照出来——在那之前，两处各自都「看起来没问题」。

### P34. 想「再抓一份数据源」前，先验证那份数据存不存在 🔴 想当然

**症状**：为了让英文页参数表不混排中文，第一反应是「管线同时抓英文官网，
存 `specs` / `specsEn` 双份」。听起来只是「再写一个适配器」的工程量问题。

**真相**：

- 华为国际站**根本没有国内站这批机型** ——
  `consumer.huawei.com/en/phones/mate90-pro-max/specs/` 实测 **404**（Mate 90 系列是中国线）；
- 就算机型对得上，规范化层 **2700+ 行**（index+parse+shared+brands，实测 2767 行）深度依赖中文正则**（`/芯片$/`、
  `/超瓷晶|昆仑/`、`/英寸/`），做英文版等于再造一份规范性真源，
  两边的「6.1 英寸」出自两套正则却互不对账。

**教训**：**先花五分钟验证数据存在性，再估工程量**。
`curl -o /dev/null -w '%{http_code}'` 一条命令就能证伪一个「大工程」。
反过来，中英两版是同一份规格的**逐条对应**（中文「超瓷晶面板 (正面)」
↔ 英文 `Ceramic Shield front`），所以术语级对照表就够用，代价是它的十分之一。
