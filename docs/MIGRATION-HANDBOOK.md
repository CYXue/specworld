# 数据驱动静态站·迁移手册

> **这份文档是干什么的**：前两份是各自项目的规范提炼（`SPEC-AI-MODEL-WORLD.md`、
> `SPEC-PHONE-SPEC-WORLD.md`），**这一份是两者的交集**——
> 把与领域无关的部分抽出来，让下一个项目第一天就拥有全部工程化能力。
>
> **来源**：参考项目 `liyupi/ai-model-world`（8 数据源 / 28,561 行 TS / Next.js 16）
> 与本地 `phone-spec-world`（4 取数通道 / 11,936 行 mjs / 零依赖手写模板）。
> 两个项目技术栈几乎相反，但**架构同构**——这正是能抽象的前提。
>
> **适用对象**：任何「数据来自不可控上游、产物是静态站、上线后无人维护」的项目。
> 典型场景：参数对比站、榜单站、目录站、行情站、观测站。

## 零、先读这一页：为什么需要这份手册

### 0.1 两个项目的对照

| 维度 | 参考项目 | 本地项目 | 是否可抽象 |
|---|---|---|---|
| 技术栈 | Next.js 16 + React 19 + TS | 零依赖 mjs 手写模板 | ✅ **技术栈可换，架构不可换** |
| 数据源 | 8 个公开 API | 4 个厂商官网 | ✅ |
| 单一入口 | `npm run sync` | `node scripts/pipeline.mjs` | ✅ |
| 入库内容 | `data/` | `data/` | ✅ |
| 产物 | `.next/out` | `dist/` | ✅ |
| 发布判据 | 内容指纹 | 内容指纹 × 模板哈希 | ✅ |
| 护栏 | 自测 224 + 闸门 20 + QA 17 | 自测 76 + 闸门 17 + QA 4 | ✅ **但数量不同、层次相同** |
| 部署 | Vercel + EdgeOne + B站Toy | GitHub Pages | ✅ |

**结论**：技术栈差异是表面的，**「取数 → 仲裁 → 闸门 → 派生 → 渲染 → 指纹 → 发布」这条链是共通的**。

### 0.2 抽象出来的七条骨架

```
① 唯一入口：一条命令跑全链路，任何一步失败立即非零退出
② 三层数据：raw（原始响应）→ normalized（契约结构）→ snapshot（入库快照）
③ 护栏三层：单元自测 + 校验闸门 + 只读体检
④ 判据：内容指纹（数据 × 模板），不是 git diff
⑤ 静态快照：产物可由数据确定性重建，运行时零请求
⑥ 文档体系：可行性 / 排查 / 契约 / 设计 / 迁移配方 五份分工
⑦ 已知缺口：明确区分「做不了」与「坏了」
```

**这七条就是这份手册的全部内容。** 其余都是实现细节。

### 0.3 一句话核心

> **产品的使命是「发布后不需要任何人维护」。
> 而无人维护的前提是：出问题时要么自动拦住，要么有人能立刻定位到是哪一层坏了。**

这句话是两个项目的共同内核。参考项目把它写在 `ARCHITECTURE.md` 第一句，
本地项目把它落在 `pipeline.mjs` 的失败即停纪律里。

## 一、骨架①：唯一入口

### 1.1 形态

**一条命令跑完全链路**，本地与 CI 共用同一个入口。

```
取数 → 归一化 → 整合/仲裁 → 派生 → 分析 → 渲染 → 发布校验 → 指纹
```

| 项目 | 入口 |
|---|---|
| 参考项目 | `npm run sync`（管线）+ `npm run sprites`（资产） |
| 本地项目 | `node scripts/pipeline.mjs`（含子步骤统一调度） |

### 1.2 纪律：失败即停

> **任何一步失败立即非零退出，不允许「带着旧数据继续往下走」。**

理由（本地项目的原话）：

> 上游官网改版时，继续跑只会产出一份**看着正常、实际残缺**的快照。

**这是无人维护的前提。** 一个「部分失败但继续」的系统，
在12 小时一次的定时任务里会**静默产出错误数据并发布出去**。

### 1.3 失败提示必须带排查顺序

```js
console.error('上游官网结构可能变了。排查顺序：');
console.error('  1. node scripts/sources/<brand>.mjs --limit 1   看单台能否解析');
console.error('  2. 检查 docs/PITFALLS.md 里的页面结构假设是否仍成立');
console.error('  3. node scripts/selftest.mjs 看是哪个断言拦住的');
```

**规范**：错误提示不能只说「失败了」，要给出**下一步点哪里**。

这在 12 小时无人值守的场景尤其重要——没人守在日志前，
所以提示本身就是排查入口。

### 1.4 参数化开关

| 开关 | 参考项目 | 本地项目 | 用途 |
|---|---|---|---|
| 联网跑 | 默认 | `--offline` 关闭 | 全量 |
| 只用缓存 | 有缓存目录 | `--offline` | CI 失败时的重跑方式 |
| 跳过取数 | 分离的 asset 步骤 | `--skip-sources` | 调试下游 |
| 只校验不写盘 | `--dry`（selftest） | `--dry` | 看报告不改数据 |

## 二、骨架②：三层数据

### 2.1 为什么分三层

| 层 | 是什么 | 入库 | 理由 |
|---|---|---|---|
| **raw** | 上游原始响应 | ❌ | 可回放、可追查；体积大且含未过滤内容 |
| **normalized** | 映射到契约的结构 | ❌ | 中间物，体积大 |
| **snapshot** | 仲裁+校验后的入库快照 | ✅ | 唯一的机器产出 |

**关键**：raw 层**必须保留**，且**必须能被重放**。
出问题时需要对比「上游当时到底返回了什么」。

**这里有个容易忽略的坑**（参考项目踩过）：
**raw 层是合规风险面。** 管线在解析时会剔除被禁字段，
但 raw 存的是**剔除之前**的原始响应——**整套拦截被绕过了**。

> **规范**：raw 层必须与「提交」彻底隔离。
> `.gitignore` + CI 显式 pathspec + 提交前校验暂存区，三道防线。

### 2.2 快照层的三条纪律

| 纪律 | 参考项目 | 本地项目 |
|---|---|---|
| **原子替换** | 有 | 有（同目录 rename） |
| **字段级溯源** | `provenance` 逐字段 | `provenance` 逐字段（41 个路径） |
| **写盘前全树扫描** | 合规兜底 | — |

**原子写为什么要同目录 rename**：

```js
// POSIX 保证同目录 rename 是原子的
writeFileSync(tmp, text);
renameSync(tmp, path);   // 要么是旧的完整文件，要么是新的完整文件
```

### 2.3 多源仲裁（只在真的有多源时才做）

**参考项目有8 个源，两两交叉**：所以它需要完整的仲裁层。

**本地项目只有 1 个源**（厂商官网），多出的 3 个通道是**同一产品的不同粒度**
（规格页 vs 对比页矩阵），所以仲裁逻辑简单得多。

> **重要**：不要照抄多源仲裁。见 §7.3 的判据。

**仲裁的两种形态**：

| 形态 | 适用 | 参考项目 | 本地项目 |
|---|---|---|---|
| **多源交叉** | 有多个独立来源 | ✅8 源 | ❌ 不适用 |
| **多粒度优先** | 同一来源的不同粒度 | — | ✅ 规格页 > 对比页 |

### 2.4 溯源到字段级，而且要记粒度

```js
// 本地：对象型字段同时登记父路径与子路径
putObject(rec, 'display.resolutionPx', value, 'apple-official', ['w', 'h']);
// → provenance['display.resolutionPx']   = 'apple-official'
// → provenance['display.resolutionPx.w'] = 'apple-official'
// → provenance['display.resolutionPx.h'] = 'apple-official'
```

**粒度差异必须显式**：`granularity` 记 `compare-matrix`，
界面标注粒度差异。**用户有权知道这个数是逐项填的还是矩阵补的。**

> **这条是本地踩出来的**（见 §8.2）：登记侧写子路径、校验侧查父路径，
> 导致 60 台全部误报。**对象型字段的溯源要登记父子两级，两侧口径必须一致。**

## 三、骨架③：护栏三层

**这是整个手册最核心的部分。** 两个项目在这一层完全同构，只是数量不同。

```
① 单元自测    测「错了也不报错」的纯函数         不联网，1 秒
② 校验闸门    数据变坏的那一刻拒绝写盘           非零退出
③ 只读体检    回答「为什么是这个结果」只读、离线、确定性
```

### 3.1 为什么三层都不可少

| 缺哪层 | 后果 |
|---|---|
| 缺① | 改解析器时静默产出脏数据，靠肉眼发现（而肉眼只能发现最明显的那个） |
| 缺② | 脏数据一路发布到线上 |
| 缺③ | 出问题只能手翻产物排查，一次几十分钟 |

### 3.2 层①：单元自测

**选测标准**（本地项目原话）：

> 只测那些**错了也不会报错、只会静默产出脏数据**的纯函数。

**清单**（从两个项目的自测内容归纳）：

| 类别 | 断言什么 |
|---|---|
| 单位归一 | per-token → per-MTok；盎司 vs 克 |
| 日期格式 | `YYYY-MM` 与精确日；时区；未来日期 |
| 量纲 | 百分数 / Elo / 自定义标度**不可混** |
| 空值语义 | `undefined !== null` 为真；`Number('') === 0` 且 `isFinite` 为真 |
| 口径 | 典型值 / 额定值必须一起返回 |
| 后缀剥离 | 服务档位别名（`-fast`）不得冒充新型号 |
| 括号区分 | `Model-R1 (May 2025)` 与 `Model-R1` 是两个对象 |
| **闸门自身** | 健康数据必须通过 + 每条闸门的触发条件必须被拦下 |
| **配置自洽** | 区间上下界没写反；必填路径指向的字段真实存在 |

**最后两条最容易漏，而它们是最重要的**：

> **闸门是「拒绝写盘」的唯一防线，它自己写错了防线就漏了。**

**规模参考**：参考项目 224 项、本地 76 项。**数量不重要，重要的是覆盖面。**

**接进 CI 的位置**：作为**第一个 job**（最便宜、失败信息最明确），失败则整条管线不启动。

### 3.3 层②：校验闸门

**原则**：

> 合理性校验不通过就**拒绝写盘并保留旧数据**，绝不「带着旧数据继续往下走」。

**闸门的设计规范**（本地项目独有的一条，很值得抄）：

> 每条闸门都必须能回答两个问题：
> 1. **它防的是哪种真实故障？**
> 2. **误报（把好数据拦下来）的概率有多大？**
>
> 答不上来的闸门不要加。

**闸门清单**（两个项目的交集）：

| 类别 | 具体 | 参考 | 本地 |
|---|---|---|---|
| 总量 | 数量低于下限 / 比上版减少 | ✅ | ✅ |
| 覆盖率 | 必填字段覆盖率下滑 | ✅ | ✅ |
| **相对跌幅** | **承重字段跌过一半** | ✅ | ❌ **本地缺** |
| 合理性 | 数值超出物理区间 | ✅ | ✅ |
| 口径 | 有值但缺口径 | — | ✅ |
| 口径 | 峰值 < 典型（串行迹象） | — | ✅ |
| 溯源 | 有值但缺 provenance | ✅ | ✅ |
| 量纲 | 同一赛制出现两种量纲 | ✅ | ✅ |
| 日期 | 发布日期在未来 / 无法解析 | — | ✅ |
| 注册 | 品牌不在注册表 | — | ✅ |
| 配置 | 区间上下界写反 | ✅ | ✅ |

> ⚠️ **本地项目缺「相对跌幅」闸门**。参考项目的教训值得抄：
> 上游挪了文件导致某核心指标覆盖率 38% → 0%，
> 而闸门只盯「比上次少 5 个百分点」——对一个本来覆盖率就不高的字段形同虚设。
>
> **凡是输出参与排名的字段，都要有相对跌幅闸门。**

**闸门会误报**（两次实证，见 §8）：

> 所以闸门自己也要被测。而且**闸门失败看起来像「数据本来就缺」时，
> 最容易被当成结构性缺口忽略掉** —— 这正是本项目那个 bug 活这么久的原因。

### 3.4 层③：只读体检

**三条纪律**：

1. **只读**——「体检」和「修复」必须是两件事。体检顺手改了数据，就没人信它的结论了。
2. **离线确定性**——同一输入产出同一输出，否则没法用它判断「这次改动引入了什么」。
3. **一个脚本只回答一件事**——输出必须短到能一眼看完。

**必备的三类脚本**：

| 类型 | 回答 | 参考项目 | 本地项目 |
|---|---|---|---|
| **解释单个** | 为什么这台/这家是榜首 | `why-flagship.ts <id>` | `why-champion.mjs --detail` |
| **影响面** | 改这条规则，全部对象会变什么 | `flagship-rules.ts` | （部分覆盖） |
| **数据体检** | 哪些字段大面积缺数据 | `roster-signals.ts` | `coverage.mjs` |
| **过期检测** | 有没有该退场的对象 | `stale-flagships.ts` | `stale-lineup.mjs` |
| **视觉自检** | 三个断点批量截图 | `shots.ts` | （有截图工具，非脚本） |

**实现要点：解释单个的脚本必须 import 同一套标尺，不能重写一遍。**

```js
// 本地：直接 import derive.mjs 的 buildChampions
import { buildScales, buildChampions, metricValue } from '../lib/derive.mjs';
```

理由：**这样看到的结论和页面上看到的一定一致**。
不一致就说明有 bug，而不是有分歧。

### 3.5 体检层的信息架构

**规范**：把「什么情况下该跑什么」写成对照表，放进项目说明文件。

```
数据看着不对       → 先跑 coverage，看缺口分类
改了解析器         → 先跑 selftest，确认基线
改了排名/选拔逻辑   → 先跑影响面脚本，看全部对象的新旧对比
改了 UI           → 截图自查（两个断点）
改完想知道影响面   → 跑全链路，看内容指纹变了没有
```

**一条规则在两三家上看着对，不等于它在四十家上是对的。**

### 3.6 缺口的三类分法（可直接复用）

这是本地项目 `coverage.mjs` 的设计，**对任何多来源项目都适用**：

| 类别 | 判据 | 含义 | 处置 |
|---|---|---|---|
| **① 结构性** | 一个来源全有、另一来源全无 | 上游不公布 | 覆盖率门槛生效，不排名 |
| **② 全站皆零** | 谁都没有 | 没人公布，或对所有来源都失手 | 查 raw 原文确认 |
| **③ 同来源内部分化** | 同一来源内有的有、有的没有 | **页面写法没解析到** | 待修队列 |

> ⚠️ **这个分类很容易写反。**
> 本地第一版按「缺失台数最多的来源是结构性」来分，
> 结果把苹果 13 台的正常字段全判成解析器失手——因为苹果只有 13 台。
> **真相正好相反：是华为官网不公布这些。**
>
> **正确判据是「某来源覆盖率接近 0、另一来源接近 1」**，与台数无关。

## 四、骨架④：内容指纹

### 4.1 为什么不能用 `git diff`

**实测过的坑**：数据文件里带一串运行时刻字段
（`generatedAt` / `fetchedAt` / `lastSeenAt` / `listedAt` / `publishedAt`），
它们每次跑都在变。

**实测数据**：连跑两次、一台对象的数据都没动，哈希照样从 `3c0a68e2` 变成 `e637e240`。

**后果链**：
```
指纹每次都不同 → 「数据无变化就跳过提交」永远不成立
              → 定时任务每 12 小时制造一次空提交
              → 下游的「内容没变就不发布」一并失效
```

### 4.2 剥哪些字段：只剥运行时刻，保留业务日期

```js
VOLATILE_KEYS = ['generatedAt','fetchedAt','lastSeenAt','firstSeenAt',
                 'retiredAt','listedAt','publishedAt','syncedAt','builtAt','snapshotAt']
```

**关键设计：只写字段名，不用路径通配。**

| 写法 | 结果 |
|---|---|
| `'generatedAt'`（字段名） | ✅ 只剥这一个概念 |
| `'*.date'`（通配） | ❌ 会误伤业务日期 |

**保留业务日期**（`releaseDate`、`windowStart`）——那是用户看得见的信息，变了就该算变化。

### 4.3 组合式指纹：数据 × 模板

```js
dataFingerprint     = hash(stripVolatile(snapshot))
templateFingerprint = hash(代码文件内容，跨 OS 归一化行尾)
siteFingerprint     = hash(dataFingerprint + templateFingerprint)
```

**为什么必须组合**：页面是「数据 × 模板」的产物，两条路都会改变用户看到的东西。

| 变化 | 用户看到的变了？ | 需要哪个指纹 |
|---|---|---|
| 上游数据变了 | ✅ | 数据指纹 |
| 模板改了（新增板块、修版式） | ✅ | 模板指纹 |
| 时间戳刷新了 | ❌（只是新鲜度） | 不触发 |

**组合式的额外好处**：**天然绕开了「在产物里剥离时间文本」的难题**——
那种做法容易把业务日期（发布日期）一起误删。

> **本地比参考项目强的地方**：参考项目只有「数据 + 代码文件内容」的单一哈希，
> 粒度更粗。本地的三段式让 CI 能分别回答「数据变了」「模板变了」「都没变」。

### 4.4 跨 OS 必须归一化行尾 ⭐

```
Windows checkout → CRLF
Linux CI         → LF
同一份代码算出两个指纹
→ 本地推一次，CI 判「站点变了」发布一次
→ CI 提交后本地又判一次变，来回空转
```

```js
hash(readFileSync(path, 'utf8').replace(/\r\n/g, '\n'))
```

> **这个坑的特征是「本地全对、CI 全对，但两边互相触发」**——
> 很容易被误判成「CI 缓存有问题」而查错方向。
> **任何跨操作系统的内容哈希，都要先归一化行尾。**

### 4.5 指针文件：入库的「线上现状」

```
data/.fingerprint        入库 —— 线上现在就是这一版
_work/fingerprint.json   不入库 —— 只在同一次 job 内流通
```

**为什么需要**：CI 每次 checkout 拿不到 `_work/`，需要入库的指针做比对。

**指针里不含时间戳**——否则每次 diff 都非空，去重又失效。

### 4.6 提交条件：两条路都要能触发

```
if (data_changed || site_changed) {
    推进指针
    if (data_changed) add -A -- data/
    else              add -- data/.fingerprint
}
```

**只改模板时数据没变但站点变了**——若不推进指针，
之后每轮都会被判成「站点有变化」，于是**每 12 小时重复发布一次同样的站点**。

### 4.7 提交安全：三道防线

```bash
# 1. 显式 pathspec
git add -A -- data/
# 2. 提交前校验暂存区
if git diff --cached --name-only | grep -Ev '^data/'; then exit 1; fi
# 3. .gitignore 覆盖所有落盘点
```

参考项目因为「缓存被误提交进公开仓库」（165 个文件、16 MB、
含 187 处被禁字段）也加了这三道。

> **规范**：`gitignore` 要覆盖**所有**落盘点，不只是你知道的那一个。
> 任何把上游响应落盘的地方（缓存、日志、artifact、调试转储）
> 都是一个独立的再分发面。

## 五、骨架⑤：静态快照

### 5.1 为什么是静态快照而非运行时拉取

**三个理由**（按重要性）：

1. **上游挂掉时网站照常显示上一次的好数据，永远不白屏。** 运行时拉取做不到。
2. **前端不碰任何 API key。** 没有密钥就没有泄漏风险，也没有需要续费的东西。
3. **提交历史本身就是一套自动积累的快照库。**
   每天两次提交，一年后就有了七百多个时间点的完整状态。
   **这个资产越早上线越值钱，而且完全免费。**

**代价**：新鲜度以「同步周期」计而非秒计。对信息站可忽略，
真要抢时效可随时手动触发一次。

### 5.2 产物可由数据确定性重建

**参考项目**：606 张精灵图不提交，构建时由「已提交的数据 + 已提交的设定表」生成。

**理由**：合成器改一次绘制逻辑就产生十几 MB 新 blob，几次迭代就把仓库撑爆。
构建时生成还有个好处：**产物必然与数据一致，不会脱节。**

**本地**：60 张SVG 立绘入库。60 台可以，**这是规模增长的第一个爆点**——
若扩到 200 台就该改成构建时生成。

> **判据**：产物体积 × 迭代次数决定要不要生成。
> 小规模入库更简单（省一个构建步骤），大规模生成更安全（不会撑爆仓库）。

### 5.3 身份层与状态层分离

| 层 | 放哪 | 理由 |
|---|---|---|
| **身份**（是什么） | 产物内烘焙 | 只有对象本身变了才变 |
| **状态**（现在怎么样） | 前端现画 | 排名每天变；有些状态必然过期 |

**好处**：排名一变当场更新，不需要重新合成任何资源。

**代价**：前端要知道元素位置，依赖实测锚点。
**不能硬编码百分比**——头顶高度会随体型、发型而变，实测能差 3 像素。

**握手信号**：产物清单里写 `overlaysBaked: false`，**前端读它而不是写死**。
读不到时**保守地认为已烘焙，宁可少画也不要画重**。

### 5.4 零外链、零密钥、零外部请求

**可验证的纪律**：

```
双击 index.html 就能看 —— 不需要起服务器、不发起任何请求
```

这条纪律排除了一整类设计（CDN 字体、远程图片、外部 API），代价是要写本地化资源。

**必须本地化的**：

| 资源 | 原因 |
|---|---|
| 字体 | Google Fonts 等在国内不可达；用系统字体栈或自托管 |
| 搜索索引 | 内联进每页（`window.__SW_INDEX__`），不单独请求 |
| 搜索脚本 | 内联，不引外部 JS |
| 样式 | 内联 `<style>` |

### 5.5 静态托管的路由行为要用最笨的服务器验证

> **「本地点得通」不等于「哪都点得通」。**

参考项目踩过：`trailingSlash` 遇到 slug 含点时不补斜杠，
近四成详情页在严格静态托管上 404。
本地 dev server 和 Vercel 都会做 `/x` → `/x/` 重定向，**所以本地怎么点都是对的**。

**规范**：
- slug 里的点转连字符
- 验证时对着**导出的文件名**核链接，别只看浏览器点得开
- 用最笨的文件服务器（如 `python -m http.server`）而不是带重定向的框架

### 5.6 发布校验清单

```
□ 外链检查          有无 http(s):// 的引用
□ 内联脚本体检       不得有外部 src
□ 相对文件存在性     <a> / <img> / <svg> 指向的文件必须存在
□ 内容纪律          「—」不得冒充数据；空值只能显示未公布
□ 关键页面存在       防止重构漏产出
□ 零失效链接
```

## 六、骨架⑥：文档体系

### 6.1 五份文档分工

| 文档 | 回答什么 | 不回答什么 |
|---|---|---|
| **契约** | 字段定义（唯一来源） | 怎么取、怎么排 |
| **可行性** | **为什么能取到**（实测证据） | 取不到时怎么查 |
| **排查** | **取不到时怎么查**（结构假设 + 决策树） | 为什么能取到 |
| **设计** | 信息设计定稿 | — |
| **迁移配方** | 怎么搬到别的项目 | 本项目的业务细节 |

**「可行性」与「排查」分开是本地特有的好设计。**
参考项目只有前者，所以改版时只能翻代码找线索。

### 6.2 HANDOFF：给下一个接手的（人或AI）

**结构模板**：

```
一、这是什么
二、当前状态（已完成 / 关键覆盖率 / 未完成）
三、快速上手（日常维护 / "更新数据"怎么做 / 体检脚本）
四、不可违背的原则        ← 最重要
五、贯穿全站的一个模式
六、踩过的坑              ← 第二重要
七、代码地图（文件 → 职责）
八、容易被误改回去的决策
九、已知缺口（诚实列出做不到的）
十、接着做什么（按优先级）
十一、产品负责人的偏好    ← 容易被忽略但价值极高
```

### 6.3 两个必抄的小节

**「不可违背的原则」**：每条都要能回答
> 改动前必须先确认是不是真的想推翻它。

**「踩过的坑」**：排序标准是
> **按「不知道就一定会再踩一次」排序。**

这一节记录的是**试过但行不通的方案**——
「刻意不做的选择」「曾经破坏过原则又回滚」的记录，
比成功路径的信息密度更高。

> **回滚也要记录**：参考项目曾为画面好看破��数据诚信原则，
> 后来回滚了，并在代码里留注释指向具体文件，
> **防止下一个人重新「优化」回去。**

### 6.4 产品负责人的偏好 ⭐（最容易被忽略）

**把历次反馈沉淀成规则，而不是当个人偏好。**

参考项目这一节记录的例子：

| 反馈 | 沉淀成的规则 |
|---|---|
| 「阅读舒服是最重要」 | 字号已上调三次，正文 14px 起，别再往小调 |
| 「不要解释性文字」 | **凡是需要解释的词，换掉它**（不是解释它） |
| 网格扫描线干扰阅读 | 任何规则重复的线条压在文字后面都会被否，无论透明度 |
| 「这一排不放源码链接」 | 但页脚署名区那行不算，两者不冲突 |

> **为什么这节值得抄**：产品决策如果不沉淀成规则，
> 下一轮开发会把它当成个人偏好而忽略掉。
> **「他明确说过的，别再撞」这句话本身就是文档价值。**

### 6.5 文档里的数字必须实测

> **不要把某个数字当契约写进文档。**

本地项目写 `PITFALLS.md` 时实测纠正了三处：

| 文档里写的 | 实测 | 差距 |
|---|---|---|
| 某页面 35 个段落 | **54 个**（三台一致） | 结构判断错了 |
| 缓存按名称命名 | 按 **哈希**命名，要靠索引反查 | 排查命令跑不通 |
| 章节 19 / 字段 44 | **16/33~19/33**，折叠屏 **18/8** | 折叠屏只有 8 个 |

由此得出的规范：

> 写文档时用实测命令验证，并注明「以实测为准」。
> **更重要的是：不要把计数当判据。**
> 上例里章节数在 8–33 之间浮动，「字段数少于 N 就是结构变了」根本不成立——
> 只能是「关键章节名还在不在」。

### 6.6 代码注释即规范

规范写在代码头部注释里（而非只写在 docs），好处是**改那个文件的人一定看得到**。

| 文件 | 头部纪律 |
|---|---|
| 入口 | 失败即停，不带着旧数据往下走 |
| 解析器 | 解析不出就 null / 口径一起出来 / 只取第一个合理数字 |
| 派生层 | 分位不用绝对阈值 / 头衔过覆盖率门槛 / 跨口径不排名 |
| 闸门 | 每条必须能回答「防哪种故障 / 误报概率多大」 |
| 渲染 | 零外链 / 缺数据显式标注 / 文案套模板不调 LLM |

## 七、领域无关的判据清单

**这一节是全文最抽象的部分**：剥掉手机和模型的具体细节后，剩下的判断规则。

### 7.1 数据层判据

| 判据 | 说明 |
|---|---|
| **没有数据就说没有数据** | 绝不用 0、`-`、平均值或估算值填补 |
| **空值必须有专属视觉形态** | 与「值是 0」一眼可辨，否则原则等于没落地 |
| **解析不出就 null** | 绝不猜、绝不兜底 |
| **口径跟着数值出来** | 典型/额定、峰值/典型——缺口径的值不许进快照 |
| **只取第一个合理数字** | 不做跨字段推断，宁可 null |
| **并列值不取平均** | 平均是编造 |
| **溯源到字段级** | 而且对象型字段要登记父子两级 |
| **多粒度差异要显式标注** | 用户有权知道这个数怎么来的 |

### 7.2 展示层判据

| 判据 | 说明 |
|---|---|
| **档位用池内分位** | 连续量映射成档位时，不用绝对阈值 |
| **问绝对时间时用阈值** | 分位不是无脑套用。「发布多久」问的是绝对时间 |
| **分位池的选择要显式** | 问「相对位置」用全体；问「这一屏里稀不稀有」用同屏 |
| **绝对数值必须另有出处** | 只给档位不给绝对值 = 把判断权交给标尺 |
| **头条衔过覆盖率门槛** | 覆盖不足时不排名，并如实说明 |
| **跨口径不排名** | 测试条件不同的数值只并列展示 |
| **不可比的量不显示排名** | 池子大小不同时，「6 个里第 2」和「25 个里第 2」都显示成「第 2」|
| **可比的表达是分位档** | 它是唯一跨池可比的表达 |
| **几何/视觉由数据算出** | 能算的绝不手绘 |
| **缺数据退回中性色** | 不猜一个好看的配色 |

### 7.3 ⚠️ 什么不能照抄

**这一节极其重要。两个项目的具体做法不能互相移植。**

| 参考项目做法 | 本地为什么不能抄 | 判据 |
|---|---|---|
| **8 源字段级仲裁** | 手机参数（PPI/厚度/电池）只有官网知道，**没有第二来源**。照搬只会造出永远只走第一票的空壳 | **多源仲裁的前提是「真的有多源」**。先确认每个字段有几个独立来源，1 个就别做仲裁 |
| **Next.js + React** | 1671 行手写模板已跑通；迁移收益是省手写模板的活，成本是重写 + 引入 300MB 构建链 + 换部署目标 | **迁移技术栈前先算「现有存量 vs 重写成本」** |
| **精灵图生成** | 本地 60 台 SVG 入库没问题，扩到 200 台才是爆点 | **产物体积 × 迭代次数**决定要不要生成 |
| **抽「能力条」等复杂可视化** | 手机圈没有可信第三方成绩源，**能力条无数据可画** | **不要做没有数据支撑的可视化** |
| **`undefined !== null` 的坑** | 通用 | ✅这条可以抄 |

**反向也不能照抄**：

| 本地做法 | 参考项目为什么不能抄 | 判据 |
|---|---|---|
| **标题级覆盖率门槛 50%** | 模型榜单数据覆盖率很高（80%+），50% 门槛会让本该发的奖杯不发 | **门槛要按自己数据的实际分布定**。先跑覆盖率体检，看分布再定线 |
| **不做跑分、不做综合分** | ✅ 两边一致，这个照抄 | — |
| **标题里保留品牌名后缀**（`HUAWEI Mate 90`） | 参考项目的 `name` 字段已含厂商 | 看字段本身是否已含 |

### 7.4 无人维护的四道防线

| 防线 | 防什么 |
|---|---|
| **原子写+ 失败即停** | 半成品落盘、带着旧数据继续 |
| **校验闸门** | 数据变坏时静默发布 |
| **内容指纹** | 空提交、无意义发布 |
| **已知缺口清单** | 有人反复尝试已证明不可行的路 |

## 八、实施踩坑记录（真实案例）

**这一节的价值是「试过但行不通」的记录，比成功路径更高。**

### 8.1 解析器少取一个值，闸门一律放行 🔴

**这是最危险的一类错误。**

| 原文 | 取错的结果 | 闸门拦得住吗 |
|---|---|---|
| `2160 Hz 高频 PWM 调光` | 刷新率 2160 | ✅ 拦得住（超出区间）|
| `2622 x 1206 像素分辨率` | 刷新率 2622 | ✅ 拦得住 |
| `60 Hz / 90 Hz 屏幕` | **只取到 60** | ❌ **拦不住** |
| `7.44盎司` | 重量 7.44 | ❌ 拦不住 |
| `12 GB RAM` 混在 ROM 字段 | 存储多出 12 | ❌ 拦不住 |

> **凡是「少取了一个值」「取到了相邻字段的值」，结果都落在合理区间内，
> 闸门没有理由拦。**

**这就是单元自测存在的理由。** 本地项目在自测写完当天就抓到了`60/90` 那个 bug——
**靠肉眼不可能发现，它看起来完全合理。**

### 8.2 闸门误报 60 次，因为它看起来像真问题 🔴

对象型字段溯源登记子路径，校验侧查父路径 → **60 台全部**报「缺 provenance」。

> **它能活这么久，恰恰因为它看起来像「数据本来就缺」，
> 被当成结构性缺口忽略了。**

**规范**：闸门自己也要被测。而且**闸门误报比闸门漏报更隐蔽**——
漏报会报错，误报会安静地被归类成「已知问题」。

### 8.3 缺口分类判反了，因为它看起来很合理 🔴

第一版按「缺失最多的来源是结构性」分类，把小样本来源的正常字段全判成解析器失手。

**真相正好相反。**

> **规范**：写分析类脚本时，**先用一个手算的小样本验证分类逻辑对不对**，
> 再跑全量。小样本下错误会立刻暴露。

### 8.4 计数不是判据 🔴

「章节数少于 N 就是结构变了」这条判据，在实测发现机型间差异 8–33 后失效。

> **规范**：判据用**「关键标识还在不在」**，不用计数。

### 8.5 跨 OS 行尾 🔴

特征：**本地全对、CI 全对，但两边互相触发**。
容易误判成「CI 缓存有问题」而查错方向。

### 8.6 合规拦截发生在解析阶段，而缓存早于解析 🔴

管线在解析时剔除被禁字段，但缓存存的是剔除**之前**的响应 → 整套拦截被绕过去。

三个放大因素：`gitignore` 漏了一个落盘点 / 缓存是 base64 存的 grep 不到 / 拦截时机晚于落盘。

> **规范**：任何把上游响应落盘的地方都是一个独立的再分发面。
> **加一个落盘点就要重做一次合规评估。**

### 8.7 统计上溢：桶只写了上界 🔴

分桶「一年内 / 1–2 年 / 2–3 年 / 超过 3 年」只按上界筛，
结果「2–3 年」和「超过 3 年」都是 60。

> **规范**：区间统计要按**下界**筛，或者**加一个「桶合计 ≠ 总数」的告警**。
> 后者更有效——它让错误自己暴露。

### 8.8 上游悄悄挪文件 🔴

上游把文件挪位置并改列名，解析器找不到 → 某核心指标覆盖率 38% → 0%，
而闸门只盯绝对跌幅 → **放行**。

> **规范**：**凡是输出参与排名的字段，都要有相对跌幅闸门。**

### 8.9 取最高分在迭代快的领域系统性偏向旧对象 🔴

评测有滞后，刚发布的旗舰还没分数→ 不参与选拔→ 榜单上摆着上一代。

> **规范**：「取最高分」在**数据有滞后**的领域会系统性偏向旧对象。
> 你的领域如果有同样问题（新品刚发布、旧品数据齐全），要显式处理这个偏差。

### 8.10 TS 语法写进 .mjs 文件 🔴

> **规范**：文档里写示例代码要确认目标语言的语法。
> Node 的 `.mjs` 不支持 `as const` / `: Type` 注解，必须用 JSDoc。

## 九、新项目第一天检查单

**从第一天就位，不要裸奔三轮再补**——
两个项目里有一个就是先跑通自动化、出了两次静默数据事故才回头补护栏的，
而事故只有最明显的那一个被肉眼抓到。

### Day 1 · 骨架

- [ ] **目录分层**：`data/` 入库、`dist/` 与中间物不入库
- [ ] **唯一入口**：一条命令跑全链路
- [ ] **失败即停**，错误提示带排查顺序
- [ ] **原子写**（同目录rename）
- [ ] **数据契约文档**：字段定义的唯一来源

### Day 1 · 指纹与发布

- [ ] 指纹脚本：剥运行时刻 + **归一化行尾**

## 十一、结语：三条不该忘的

**从两个项目的实践里提炼的三句话。**

### 1. 「没数据」和「数据是0」必须长得不一样

这是全部纪律里最容易被违反、后果最不可见的一条。
一个假的数字比一句「暂无数据」有害得多。

### 2. 闸门挡不住「少取一个值」

凡是不在合理区间里的错误，闸门都能拦。
凡是**仍在合理区间内**的错误——少取一个值、取到相邻字段——
闸门一律放行。

所以单元自测不是形式主义，是唯一能拦住这类错误的手段。

### 3. 出问题时能定位到哪一层坏了，比出问题时自动恢复更重要

无人维护的前提不是「永不出错」，
而是「出错时要么自动拦住，要么有人能立刻定位」。

护栏三层 +五份文档 + 排查决策树，服务的是后者。
