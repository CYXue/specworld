## 一、架构三条硬规矩

这三条写在 README 与 `docs/AUTOMATION-RECIPE.md` 里，**每条都有对应的真实事故支撑**。

### 1.1 入库的只有 `data/` 与代码；产物与中间物一律不进库

```
data/          ← 入库：唯一的机器产出（快照 + 人工核对的取证表 + 指纹指针）
dist/          ← 不入库：站点产物，任何人 4 秒可重建
_work/         ← 不入库：原始响应、HTTP 缓存、分析层中间物
src/ scripts/  ← 入库：代码
```

**理由**：产物可由代码 + 数据确定性重建，入库只会制造同步冲突。

**判据**：任何人跑 `node scripts/pipeline.mjs --offline`（约 4 秒）就能重建全部 76 页。

**代价与收益**：CI 每次 checkout 拿不到 `_work/`，所以需要 `actions/cache` 恢复 HTTP 缓存。
**注意**：`_work/` 里有一个真实事故——`data/release-dates.json`（人工核对的取证表）
曾经躺在 `_work/` 里被 gitignore，CI 全新 checkout 拿不到，
60 台全部因「无发布日期」被窗口过滤丢掉，同步每一次都失败。
**人工产出的数据必须在 `data/` 里。**

### 1.2 判据是内容指纹，不是 `git diff`

**为什么不能用文件哈希**（实测踩过）：

`data/products.json` 里带一串运行时刻字段：
顶层 `generatedAt`、每台机器的 `firstSeenAt` / `lastSeenAt` / `retiredAt`、
每个 SKU 的 `listedAt`、每个源的 `fetchedAt`。

**实测**：连跑两次、一台机器的数据都没动，哈希照样从 `3c0a68e2` 变成 `e637e240`。
后果是「数据无变化就跳过提交」永远不成立 → CI 每 12 小时制造一次空提交 → 下游的「内容没变就不发布」一并失效。

### 1.3 用户看得见的东西变了才发 Pages

`deploy` job 的 `if` 条件读的是**站点指纹**，不是数据指纹。

## 二、内容指纹：本地比参考项目强的设计 ⭐

### 2.1 组合式指纹

```js
dataFingerprint    = hash(剥掉运行时刻字段后的 products.json)
templateFingerprint= hash(scripts/**/*.mjs 的文件内容)  // 只哈希参与构建的 .mjs；纯文档型 .ts 不计入
siteFingerprint    = hash(dataFingerprint + templateFingerprint)
```

**为什么必须组合**：页面是「数据 × 模板」的产物，**两条路都会改变用户看到的东西**：

| 变化 | 影响 | 需要的指纹 |
|---|---|---|
| 官网数据变了（新机发布、价格调整） | 页面内容变 | 数据指纹 |
| 模板改了（新增板块、修版式） | 页面内容变 | 模板指纹 |

反过来，页面里的「数据快照 2026-10-02 15:01 UTC」是给用户看新鲜度的，
每次都变但**不该触发发布**。

**组合式指纹天然绕开了「在 HTML 里剥离时间文本」的难题**——
那种做法容易把业务日期（发布日期）一起误删。

> **与参考项目的差异**：
> 参考项目只有「数据 + 代码文件内容」的单一哈希，粒度更粗。
> 本地的三段式（数据 / 模板 / 组合）让 CI 能分别回答
> 「数据变了」「模板变了」「两者都没变」，并在提交信息里说清楚是哪一种。

### 2.2 剥哪些字段：只剥「运行时刻」，保留业务日期

```js
VOLATILE_KEYS = ['generatedAt','firstSeenAt','lastSeenAt','retiredAt',
                 'listedAt','fetchedAt','publishedAt','syncedAt',
                 'builtAt','snapshotAt']
```

**关键设计：只写字段名，不写路径后缀。**
因为要剥的是「时间戳」这一个概念，不是「所有叫xxx 的字段」。
如果写成 `'*.firstSeenAt'` 这种通配，就会误伤业务日期。

**保留业务日期**（`releaseDate`、`windowStart`）——那是用户看得见的信息，变了就该算变化。

### 2.3 指针文件：入库的「线上现状」

```js
data/.fingerprint   // 入库，随数据一起提交
_work/fingerprint.json  // 不入库，只在同一次 CI job 内流通
```

**为什么需要指针**：`data/.fingerprint` 是「线上现在就是这一版」的记录，
下一次 CI checkout 时读它做比对。**不入库**就无从比对。

**指针文件里不含时间戳**，否则每次 `git diff` 都非空，去重又失效。

### 2.4 踩过的坑：CRLF 与 LF（本地独有，参考项目没遇到）

```
Windows checkout → CRLF
Linux CI         → LF
同一份代码算出两个模板指纹
→ 本地推一次，CI 就判「站点变了」发布一次
→ CI 提交后本地又判一次变，来回空转
```

**修法**：读文件后先 `.replace(/\r\n/g, '\n')` 再哈希。

> **可迁移判据**：
> **任何跨操作系统的内容哈希，都要先归一化行尾。**
> 这个坑的特征是「本地全对、CI 全对，但两边互相触发」——
> 很容易被误判成「CI 缓存有问题」而查错方向。

### 2.5 提交条件：两条路都要能触发

```
if (data_changed == true || site_changed == true) {
    推进指针
    if (data_changed) git add -A -- data/
    else              git add -- data/.fingerprint
}
```

**只改模板时数据内容没变，但站点变了**——若不推进指针，
之后每轮都会被判成「站点有变化」，于是每 12 小时重复发布一次同样的站点。

**外加一道显式 pathspec 白名单**：

```bash
git add -A -- data/          # 显式 pathspec
if git diff --cached --name-only | grep -Ev '^data/'; then
    echo "::error::暂存区出现了 data/ 以外的文件，拒绝提交"; exit 1
fi
```

参考项目因为同类事故（缓存被误提交进公开仓库）也加了这条，
**两家的做法一致：显式 pathspec + 提交前校验暂存区**。

## 三、数据诚信：与参考项目同源，但更细到解析层

### 3.1 解析层的铁律（`scripts/normalize/parse.mjs` 头部）

```
1. 解析不出来就返回 null，绝不猜、绝不兜底成 0。
   「没有数据」和「数据是 0」在界面上必须长得不一样。
2. 口径跟着数值一起出来。
   电池 mAh 是典型值还是额定值、亮度是峰值还是典型，
   解析函数必须把它一并返回，缺口径的数值不许进快照（闸门会拦）。
3. 只认「第一个合理数字」，不做跨字段推断。宁可 null，不要错。
```

**这三条比参考项目的「没有数据就说没有数据」更细一档**：
参考项目是在**渲染层**区分，本项目在**解析层**就拒绝产生假值。

### 3.2 闸门第 7 条把纪律 2 变成强制

```js
if (has(p.battery?.capacityMah) && !p.battery.capacityCaliber) {
    fail.push(`${p.id} 有电池容量但缺 capacityCaliber（口径不可缺失）`);
}
```

**为什么这是好设计**：纪律写在注释里会被忽略，写进闸门就绕不过去。

### 3.3 界面层的对应表达

```js
export const unpub = (lang) => `<span class="unpub">${...官方未公布...}</span>`;
```

**判据**：如果界面上「没有数据」和「数据是 0」长得一样，这条原则就等于没落地。

### 3.4 已知「官网真没有」（不是没解析到）

`scripts/normalize/index.mjs` 头部显式列出：

| 缺口 | 处置 |
|---|---|
| 苹果从不公布电池容量(mAh)、RAM、充电器额定功率 | 一律 null |
| 华为 50 台里 20 台官网没有「处理器」章节 | `chipset.name = null`，**绝不从型号名猜** |
| 华为规格页不公布屏幕亮度(nits) | null |
| 苹果对比页不公布电池容量 | null |

**这条清单的价值**：把「解析器失手」与「官网不公布」分开。
`scripts/qa/coverage.mjs` 把缺口分成三类，正是为了自动做这个区分。

### 3.5 跨口径不排名

厂商标称续航（苹果「视频播放 34 小时」vs 华为「视频播放 X 小时」）
测试条件不同，**只并列展示，不参与任何排序**。

## 四、头条衔的覆盖率门槛（本地首创的做法）

### 4.1 规则

```js
TITLE_COVERAGE = 0.5   // 覆盖率门槛
TITLE_MIN_POOL = 6     // 最少参赛数
```

覆盖率不足时**不发奖杯**，返回 `insufficient` 让界面如实说明。

### 4.2 为什么必须这样

电池容量只有华为公布（苹果 13 台全部为空）——
如果不管覆盖率就发「电池最大」的奖杯，
等于把「唯一公布数据的品牌」说成「最强的品牌」。

**实测数据**：峰值亮度只有 13/60 台公布（21.7%）→ 首页不发「屏幕最亮」奖杯；
电池容量 47/60（78.3%）→ 发奖杯，但竞争只在华为 47 台内部。

> **可迁移判据**：
> **任何跨对象比较的指标，都要先看覆盖率再决定是否排名。**
> 覆盖率低到一定程度，「最强」这个说法本身就是错的。

### 4.3 查这个结论用体检脚本

```bash
node scripts/qa/why-champion.mjs --detail
```

它直接 `import { buildScales, buildChampions }`——**复用同一套标尺**，
所以体检看到的结论和页面上看到的一定一致。不一致就说明有 bug，而不是有分歧。

## 五、档位一律用池内分位（与参考项目同源）

```
档位一律用「当前池内的分位」，不用绝对阈值。
三年后手机普遍更重更贵，写死阈值不会报错，只会悄悄失效。
```

**与参考项目完全一致的理由**。本项目原话补充了手机领域的具体后果：

> 写死阈值不会报错，只会悄悄失效。

**唯一的例外也是唯一必须例外的**：`stale-lineup.mjs` 里的「过时」判定用**绝对天数**（730 天），
因为「发布多久」这个问题问的是绝对时间，不是相对位置。

**这说明分位不是无脑套用**——**问的是相对位置就用分位，问的是绝对时间就用阈值。**

## 六、管线纪律

### 6.1 全链路唯一入口 + 失败即停

```js
/** scripts/pipeline.mjs */
纪律：任何一步失败立即非零退出，不允许「带着旧数据继续往下走」。
```

理由写得很清楚：**上游官网改版时，继续跑只会产出一份看着正常、实际残缺的快照。**

失败时的错误提示直接给出**排查顺序**（而不是只报错）：

```
上游官网结构可能变了。排查顺序：
  1. node scripts/sources/<brand>.mjs --limit 1   看单台能否解析
  2. 检查 docs/PROBE-FINDINGS.md 里的页面结构假设是否仍成立
  3. node scripts/sync/validate.mjs 看是哪个闸门拦住的
```

### 6.2 原子写

```js
function atomicWrite(path, text) {
    writeFileSync(tmp, text);
    renameSync(tmp, path);   // 同目录 rename：要么是旧的完整文件，要么是新的完整文件
}
```

**同目录 rename 是 POSIX 保证的原子性**。中途崩溃不会留下半个文件。

### 6.3 三通道取数与优先级

```
A. 华为规格页    _work/huawei.raw.json
B. 苹果规格页    _work/apple.raw.json
C. 苹果对比页    _work/apple-compare.raw.json   粒度更粗，只补规格页拿不到的机型

优先级：规格页 > 对比页矩阵。同一字段两处都有 → 用规格页，矩阵只填空缺。
走通道 C 的机型 granularity 记 compare-matrix，
相应字段 provenance 记 apple-compare。
```

**这是本地的「多源」形态**：与参考项目的 8 源仲裁不同，
本地的 3 个通道是**同一产品的不同粒度**，不是互相印证的数据源。

**粒度差异必须显式**：`granularity` 与 `provenance` 都记上，
界面标注粒度差异。**用户有权知道这个数是逐项填的还是矩阵补的。**

### 6.4 字段级 provenance，三路径登记

```js
// 对象型字段同时登记父路径与子路径
putObject(rec, 'display.resolutionPx', rec.display.resolutionPx, ap, ['w', 'h']);
// → provenance['display.resolutionPx']   = 'apple-official'
// → provenance['display.resolutionPx.w'] = 'apple-official'
// → provenance['display.resolutionPx.h'] = 'apple-official'
```

**这是一条被真实 bug 教出来的规范**（详见第八节）。

## 七、站点生成纪律

### 7.1 零外链、零密钥、零外部脚本

```
纪律：
  - 零外链、零密钥、零外部请求；双击 index.html 即可浏览
  - 文案由数据套模板，不调用 LLM
  - 缺数据显式标注「官方未公布」，绝不用 0 或 — 冒充
  - 搜索索引内联为 window.__SW_INDEX__，每页自带
```

**「双击 index.html 就能看」是一条可验证的纪律**——
它排除了任何需要起服务器、发起请求、或依赖 CDN 的设计。

**字体全本地化**：CSS 里 `--sans` 用系统字体栈，不引 Google Fonts（国内不可达）。

### 7.2 发布校验：6 项

`scripts/publish/verify-dist.mjs` 在产出后逐项检查（原 `verify.mjs` 已在 2026-10-04 清理中删除）：

1. 复制成 `dist/`（自包含发布目录）
2. 注入 `<base>`（相对路径发布时浏览器自动补全）
3. **外链检查 + 内联脚本体检**
4. **本地 `<a>` / `<svg>` 检查：指向的相对文件必须存在**
5. **内容纪律检查**：
   - 5a.「—」不得冒充数据。空值只能显示「官方未公布」
   - 5b. 关键页面必须存在（防止某次重构漏产出）
6. 数据快照 + 指纹

**第 4 项是参考项目付出代价换来的**（它的近四成详情页在严格静态托管上 404，
因为「本地点得通」不代表「哪都点得通」）。

**第 5b 项是本地特有的**：静态站的页面清单是手写的，
重构时容易漏产出某个页面。所以「关键页面必须存在」是硬检查。

### 7.3 像素立绘：一切几何由数据算出

```
设计纪律：
1. 一切几何由数据算出，不手绘：
   机身宽高比 ← 屏幕对角线，镜头数量 ← 后摄数，机身圆角 ← 厚度。
   任何一台机器的图，改一个字段就跟着变。
2. 配色不编造：数据里的 body.colors 目前两边都没抓到
   → 背面用品牌中性色
```

**第 1 条与参考项目的「身份/状态分层」是同一个思路**：
能从数据算出来的绝不手绘。

**第 2 条值得抄**：**缺数据时退回品牌中性色，而不是猜一个好看的配色。**

> **现状（2026-10-03）**：生成器 `scripts/sprite/generate.mjs` 仍在，并在管线构建期运行；但产物 `data/sprites/` 已写入 `.gitignore` 不再入库，且未接入任何页面（产品侧判定视觉效果不佳）。

## 八、护栏三层（2026-10-03 补齐）

### 8.1 三层的分工

```
① 单元自测    scripts/selftest.mjs        79 项断言，不联网，1 秒
② 校验闸门    scripts/sync/validate.mjs  拒绝写盘 + 非零退出
③ 只读体检    scripts/qa/                三个脚本，回答「为什么是这个结果」
```

**接进 CI 的位置很关键**：`selftest` 是第一个 job，1 秒、不联网，
失败则整条管线不启动——**因为它最便宜，且失败信息最明确**。

### 8.2 自测的选测标准

```
测那些「错了也不会报错、只会静默产出脏数据」的纯函数。
```

具体清单：零宽字符 / 键名归一 / 单位解析 / 电池口径 / 存储档位 / 分辨率 /
**刷新率（历史事故高发区）** / 重量亮度 / 切片 slug / **校验闸门自身** / **i18n 字典**。

### 8.3 闸门本身会被测（两次实证）

**第一次**：`display.resolutionPx` 是 `{w,h}` 对象，
规范化层登记子路径 `.w`，闸门查父路径 → **60 台全部**报「缺 provenance」假警。

> 这条能活这么久，恰恰因为它看起来像「数据本来就缺 provenance」，
> 被当成结构性缺口忽略了。**闸门自己也会误报，所以它需要被测。**

**第二次**（设计 i18n 时）：
`auditDict()` 第一版把 `site` / `nav` 这些**分组节点**也当成叶子查「缺 zh 分支」，
报出 22 条毫无意义的错。

### 8.4 体检层的三类分法（`coverage.mjs`）

```
① 结构性缺口—— 一个品牌全有、另一个全无 = 官网不公布
② 全站皆零     —— 谁都没有，需确认官网到底有没有
③ 同品牌内部分化 —— 最可疑，通常是某几种页面写法漏了解析
```

**第③ 类是解析器失手的信号，第 ① 类是官网事实。**
混在一起看会把「苹果 13 台没有电池容量」误读成大面积数据缺失。

> **踩过的坑**：第一版按「缺失台数最多的品牌是结构性」来分，
> 结果把苹果 13 台的正常字段（芯片名、防护等级）全判成解析器失手——
> 因为苹果只有 13 台，任何苹果独有的字段看起来都像「只有它缺」。
> **真相正好相反：是华为官网不公布这些。**
>
> **正确判据是「某品牌覆盖率接近 0、另一品牌接近 1」。**

## 九、护栏的接入与自动化

### 9.1 CI 结构

```yaml
jobs:
  selftest:                # 第一个 job，1 秒，不联网
  sync:                    # needs: selftest
    steps: 恢复 HTTP 缓存 → 跑全链路 → 判断指纹 → 提交变化 → 上传产物
  deploy:                  # needs: [sync, selftest]
```

**零依赖设计**：`setup-node` 之后**不装任何包**——
全链路只用 Node 内置模块，HTML 解析是手写正则与状态机。

> 「少一个装包失败点，也让 12 小时无人值守少一件能坏的东西。」

### 9.2 失败留痕

「零维护」承诺失效时必须留下看得见的痕迹：
找标题为「数据同步失败」且仍open 的 issue，有就追加评论，没有就新建。

**连续失败不会刷出一堆 issue**，修好之后手动关掉那一条即可。

### 9.3 定时与手动双触发

```yaml
schedule: cron '40 1,13 * * *'    # UTC，对应北京时间 09:40 / 21:40
workflow_dispatch:                 # 抢时效时手动整轮跑（不到一分钟）
  inputs: offline / force_publish
```

**cron 避开整点**（整点是高峰排队）。

`push` 触发条件匹配 `scripts/**`、`data/release-dates.json`、`data/products.json`、
`public/fonts/**`、`src/**` 等——**bot 提交的 data/ 也命中这里，会再触发一轮，
但因指纹不变不会再次 push，故不会死循环，只是多跑一次无害的冗余 run。**

## 十、文档体系

### 10.1 文档分工明确（12 份）

| 文档 | 回答什么 | 不回答什么 |
|---|---|---|
| `DATA-CONTRACT.md` | 字段定义（唯一来源） | 怎么取、怎么排 |
| `PROBE-FINDINGS.md` | **为什么能取到**（可行性证据） | 取不到时怎么查 |
| `PITFALLS.md` | **取不到时怎么查**（结构假设 + 排查决策树） | 为什么能取到 |
| `COMPARE-DESIGN.md` | 对比页信息设计定稿 | — |
| `MIGRATION-HANDBOOK.md` | 迁移手册：两项目交集 + 可迁移骨架 | 本项目的业务细节 |
| `BENCHMARK-VS-AMW.md` | 与参考项目的架构对标 | — |
| `ENGINEERING-REVIEW.md` | 工程评审 + 建议落地表 | — |
| `PRINCIPLES.md` | 不可违背原则总纲（数据诚信 / 零AI 依赖 / …） | — |
| `AUTOMATION-RECIPE.md` | 自动化发布配方（怎么迁移到别的项目） | 本项目的业务细节 |
| `SPEC-PARAMETER-WORLD.md` | 本项目规范提炼 | 参考项目怎么做 |
| `SPEC-AI-MODEL-WORLD.md` | 参考项目规范提炼 | 本地怎么做 |
| `REFACTOR-LOG.md` | 重构落地记录（可版本化变更日志） | — |

**`PROBE-FINDINGS` 与 `PITFALLS` 的分工是本地特有的好设计**：
一个讲「为什么能取到」，一个讲「取不到时怎么查」。

**`MIGRATION-HANDBOOK` / `BENCHMARK-VS-AMW` / `ENGINEERING-REVIEW` / `PRINCIPLES` 是 2026-10-03 补齐的「防退化工程化」文档。**
参考项目只有前者，所以它改版时的排查要靠翻代码。

### 10.2 文档里的数字必须实测

`PITFALLS.md` 初稿里的三个数字全是错的，写文档时逐一实测纠正：

| 文档里写的 | 实测 | 差距 |
|---|---|---|
| 苹果 `role="table"`，35 个段落 | `role="rowgroup"/"row"/"cell"`，**54 个**（三台一致） | 结构判断错了 |
| 华为缓存按 slug 命名 | 按 **sha1** 命名，要靠 `index.json` 反查 | 排查命令跑不通 |
| 华为 19 章节 / 44 字段 | mate70=**16/33**、mate90-pro=**19/33**、mate-x7=**18/8** | 折叠屏只有 8 个字段 |

> **由此得出一条规范**：
> **不要把某个数字当契约写进文档。**
> 手机章节数在 8–33 之间浮动，「字段数少于 N 就是结构变了」这条判据**根本不成立**，
> 只能是「关键章节名还在不在」。
>
> 写文档时用 `grep -c` 实测，并注明「以实测为准」。

### 10.3 代码注释即规范

本项目的规范**大量写在文件头部注释里**（而非只写在 docs），
好处是改那个文件的人一定看得到：

| 文件 | 头部纪律 |
|---|---|
| `pipeline.mjs` | 失败即停，不带着旧数据往下走 |
| `parse.mjs` | 解析不出就 null / 口径一起出来 / 只取第一个合理数字 |
| `analyze.mjs`（已删除，派生逻辑见 `derive.mjs`） | 能力条不做综合评分 / 缺数据 null / 分位只在同分类池内 / 类比可复算 |
| `derive.mjs` | 分位不用绝对阈值 / 头衔过覆盖率门槛 / 跨口径不排名 |
| `validate.mjs` | **每条闸门必须能回答：防哪种真实故障？误报概率多大？** |

最后那条是本地最独特的一条规范：

```
闸门的设计原则抄自「AI 大模型世界」：闸门只做一件事——
在数据变坏的那一刻拒绝写盘，保留上一版。
每条闸门都必须能回答两个问题：
  1. 它防的是哪种真实故障？
  2. 误报（把好数据拦下来）的概率有多大？
答不上来的闸门不要加。
```

## 十一、已知的结构性缺口（不是 bug）

**诚实列出做不到的部分，接手时不要以为是 bug。**

### 11.1 苹果 13 台全部缺电池容量

官网从不公布。所以「电池最大」是华为 47 台的内部竞争。
**覆盖率门槛已在 `derive.mjs` 生效**，不排名就是最诚实���处理。

### 11.2 华为约 20 台缺芯片名

官网没有「处理器」章节。**绝不从型号名猜**。

### 11.3 不做跑分评分

```
手机圈没有可公开核查的第三方成绩源
（安兔兔需登录、Geekbench 无公开 API、3DMark 收费）。
```

所以本站不给性能分，只展示官方客观参数。
`scores` 字段在契约里**刻意预留但恒为空**。

**这个「跑分缺席就是缺席」的立场与参考项目完全一致**——
两边都因为「没有可信第三方源」而拒绝造综合分。

## 十三、可直接迁移的检查单

面向「新建一个数据驱动静态站」，从本地实践提炼：

### 架构

- [ ] 入库的只有数据层；产物可由代码 + 数据确定性重建
- [ ] **人工产出的数据（取证表、配置）必须在入库目录里**，别放中间目录
- [ ] 唯一入口编排全链路；**任何一步失败立即非零退出**
- [ ] 原子写（同目录 rename）

### 指纹与发布

- [ ] 内容指纹 = 数据指纹 × 模板哈希（组合式）
- [ ] 只剥运行时刻字段，**保留业务日期**；只写字段名不用通配
- [ ] **跨 OS 哈希前归一化行尾**
- [ ] 入库一个「线上现状」指针文件，**不含时间戳**
- [ ] 提交条件覆盖「数据变了」**或**「模板变了」两条路
- [ ] 显式 pathspec 白名单 + 提交前校验暂存区

### 数据诚信

- [ ] 解析不出来就 null，**绝不猜、绝不兜底成 0**
- [ ] 口径跟着数值一起出来（典型/额定、峰值/典型）
- [ ] 闸门强制口径缺失就拦
- [ ] 界面层空值有专属视觉形态
- [ ] 列出「官网真没有」清单，**与「解析器失手」分开**

### 排名与展示

- [ ] 档位用**池内分位**，不用绝对阈值（**问绝对时间时例外**）
- [ ] 跨口径不排名（厂商标称续航 vs 实测）
- [ ] **头条衔过覆盖率门槛**，不足时如实说明「官方数据不足，本站不排名」
- [ ] 多粒度来源显式标注（`granularity` + 逐字段 `provenance`）

### 护栏

- [ ] 单元自测：覆盖「错了也不报错」的函数 + **闸门自身**
- [ ] 校验闸门：拒绝写盘 + 保留旧数据 + 非零退出
- [ ] 每条闸门能回答「防哪种故障 / 误报概率多大」
- [ ] 承重字段加**相对跌幅**闸门
- [ ] 只读体检：影响面 / 解释单个 / 数据体检
- [ ] 缺口分类：结构性 vs 全站皆零 vs 同品牌内部分化

### 站点

- [ ] 零外链、零密钥、零外部请求；**双击 index.html 就能看**
- [ ] 字体全本地化（不引 Google Fonts）
- [ ] 发布校验：外链 / 相对文件存在性 / 内容纪律 / 关键页面存在
- [ ] 几何由数据算出，不手绘；**缺数据退回中性色不猜**

### 文档

- [ ] 五份文档分工：契约 / 可行性 / 排查 / 设计 / 迁移配方
- [ ] **文档里的数字必须实测**，并注明「以实测为准」
- [ ] 代码注释即规范：每个文件头部写清纪律
- [ ] 已知缺口：明确区分「做不了」与「坏了」

### CI

- [ ] 自测作为第一个 job（最便宜、失败信息最明确）
- [ ] 不装依赖，只用 Node 内置模块
- [ ] 失败开 issue，连续失败不刷屏
- [ ] cron 避开整点
- [ ] `push` 触发路径含 `data/products.json` 等，bot 提交会再触发一轮，但靠指纹判变（不变则不 push）自愈，不会死循环
