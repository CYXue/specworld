## 一、数据诚信：不可违背的第一原则

### 1.1 核心表述

> **没有数据就说没有数据。** 绝不用 0、`-`、平均值或估算值填补空缺。

原项目的理由值得逐字抄下来：「一个假的数字比一句『暂无数据』有害得多」——
因为这个站的使命是让人看到**真实状态**。

### 1.2 落地方式：空值必须有专属的视觉形态

这条原则不能只写在文档里，必须**在渲染层强制**。原项目的四种表达：

| 场景 | 不能用 | 必须用 |
|---|---|---|
| 能力条缺数据 | 零长度的条 | **带描边的空槽**（「没测过」与「得了零分」一眼可辨） |
| 没上榜的模型 | 给个假分数 | 显示「未参赛」 |
| 参数量未公开 | 留 0 | **套雾化斗篷** + 明确标注 |
| 厂商自报成绩 | 和第三方成绩一样 | 数字旁缀一个「自报」 |

**判据**：如果界面上「没有数据」和「数据是 0」长得一样，这条原则就等于没落地。

### 1.3 这条原则的另一面：**没数据 ≠ 当它不存在**

原项目在门面选拔上栽过一次。原规则取该厂商评分最高的模型，
而评测有滞后——刚发的旗舰往往还没分数，于是「没被测过」被当成了「不够格」。

实测后果：某模型发布两个月后，广场上仍站着它的上一代。
**对一个以「一眼看懂当下格局」为使命的站点，这是实打实的误导。**

修法：加「代际接班」规则（见§2.4）。

> **可迁移的判据**：「取最高分」这类规则，在**数据有滞后**的领域会系统性偏向旧对象。
> 你的领域如果有同样问题（新品刚发布、旧品数据齐全），一定要显式处理这个偏差。

### 1.4 曾经的自我破坏与回滚（值得抄这个记录方式）

原项目试过让门面在打分持平时优先选有编程成绩的模型——
广场上「有电脑的屋子」从 4 家翻到 8 家，画面明显更好看。
但它把某旗舰 4.6 换成了 4.5、把某模型 Max 换成了 Preview 版。**拿准确性换观感，撤掉了。**

**值得抄的是这个动作本身**：在代码里留下注释说明「这里曾经为了画面好看破坏过原则，已回滚」，
并指向具体文件（`src/lib/roster.ts`）。这样下一个人不会重新「优化」回去。

## 二、自校准分位：贯穿全站的一个模式

### 2.1 表述

> **凡是把连续量映射成档位的地方，一律用「当前全体对象的分位数」，不用写死的阈值。**

原项目有 **8 处**这么做：体型档位、价格档位、能力横条填充、性价比、
标签稀有度裁剪、视觉元素裁剪、接班「分数打平」阈值。

### 2.2 为什么必须这样

**理由一：写死阈值会让档位失效。**
同一时刻的旗舰定价高度聚集，绝对阈值会把它们全塞进同一档——
广场上所有大厂角色一样高、穿一样的衣服。

**理由二（更重要）：写死阈值会随时间悄悄烂掉。**
token 价格逐年下降、上下文窗口普遍变大，若干年后所有对象都掉进最低档。
而这正是一个「发布后没人维护」的站点**最危险的失效方式**——
**因为它不会报错，只会慢慢变得毫无意义。**

### 2.3 代价与前提

- 档位表达的是「在当前这批里算大/贵/强」而非绝对值。
  对展示「当下格局」的站点，这个相对语义反而更贴近用户想问的问题。
- **绝对数值必须始终在别处如实显示**（原项目放在详情页的属性面板里）。
  只给档位不给绝对值，就是把判断权交给了标尺。
- **分位池的选择要显式**。原项目有唯一的例外：
  「稀有度裁剪」问的是「这一屏里这个元素是不是太常见」，
  所以**只喂同屏展示的那批**——「百万记性」放在 484 个里算稀有，
  放在一屏旗舰里就人手一块了。

> **可迁移的判据**：
> 「这批数据里有**同质化聚集**」（旗舰扎堆、分数集中在某个区间）时，
> 绝对阈值会把所有人压进同一档，必须用分位。

### 2.4 配套：代际接班（自校准思路的第五处应用）

**规则**：先选出评分冠军，再看有没有被自家更新的型号接班。接班满足其一：

1. **分数打平且更新**。「打平」阈值 = **全体相邻名次差的 90 分位数**——
   比九成的相邻名次差还小的差距，不足以支撑一个二元判断。
   阈值自校准：上榜模型变多时相邻差整体变小，阈值自动收紧。
2. **还没分数，但价格档不低于在位者**。价格档是厂商自己对产品定位的声明；
   同档或更高价、且晚至少 7 天发布，是「这是新一代主力」的强信号。
   反过来更便宜的新型号是同代小杯，**不构成接班**。

**验证方式**：这条规则在 42 家厂商里只改变 2 家——正是出问题的那两家，其余全部不变。
**改动足够外科手术，说明规则抓的是真问题而不是在乱动。**

**两个刻意不做的选择**（示范了「不做什么」比「做什么」更重要）：

1. **不解析型号里的版本号。**「GPT-5.6 > GPT-5.5」看着好判断，
   但 `Muse Glimmer 30B`、`Claude Fable 5` 这类命名没有可靠的版本位——
   **一条在多数对象上失灵的启发式，比没有规则更糟。**
2. **不用「最近 N 天」的固定窗口圈当代。**试过 45/60/90 天都会误伤：
   60 天窗口把有分数的旗舰挤出当代，换上了没分数的小杯。

> **可迁移的判据**：改这类选拔规则前，先跑一个「影响面」脚本，
> 列出全部对象的新旧对比。**一条规则在两三家上看着对，不等于它在四十家上是对的。**

## 三、合规红线

这一节是**产品与法律层面的硬约束**，改动前必须先确认是不是真的想推翻它们。

### 3.1 禁止性红线（两例，示范「怎么把红线钉死」）

**案例 A：某评测站（AA）的数据被条款逐字禁止**

条款 2.5 Anti-Competitive Restrictions 禁止将数据用于
「以 benchmarking / ranking / comparison 为主要目的」的产品。

加重细节（这四条是原项目逐条核实的）：

1. **免费层同样适用。** 条款对照表里 Pro 与 Commercial 两栏该条都是勾选，免费 API 另写internal use only。
2. **靠「只用衍生数据」绕不开。** 第 1.10 条明确把
   *raw Data points republished in any format* 排除在衍生数据之外，
   而按对象逐个显示分数，正是可个体识别的原始数据。
3. 第 2.4(d) 条单独禁止「把 Data 与第三方来源合并成一个对外提供的产品」——
   那恰好是该项目整条管线在做的事。
4. 违反责任**不封顶**，另有赔偿义务，且对方会主动监测。

**技术上它会经由第三跳混进来，且名字完全中性**——
所以只按名字过滤会全部漏网。判断逻辑按**名字 + 来源域名双线**，
写盘前还有一道全树扫描兜底。

> **可迁移的方法论**：
> 合规红线不能只写「我们不用 X」。要回答**「X 会不会经由第三方绕回来」**——
> 这是最容易漏的一环，也是最容易被法务追问的一环。

**案例 B：某竞技场站（抓取禁止，但官方数据集可读）**

- **抓站永远禁止。** `robots.txt` 至今仍是 `Disallow`。
- 但权利人在 Hugging Face 上以 **CC-BY 4.0** 发布了官方数据集——
  **读它与抓站在法律性质上是两回事**：前者有明示授权，后者没有。
- 接入时三条约束写死在代码里：
  1. 该站分数是人类盲投的 Bradley-Terry 分，**单独成榜、绝不进综合分**；
  2. `sourceUrl` 指向**数据集**而不是站点域名，好让合规闸门继续严格拦站点域名；
  3. 某个分榜故意不接——它有 10606 行、107 页请求，会把限流打满并连累后面的分榜。

### 3.2 边界划在哪：聚合器只做「事实字段」兜底

原项目允许从聚合器取**可独立核实的事实**（定价、上下文、模态——厂商自己公开的数字），
但**不转存原始JSON、不展示它们的自由文本**（描述、标签）。

> **可迁移的判据**：聚合器的 ToS 措辞常极宽，
> 公开展示其元数据的站点有被解读为「竞争性服务」的风险。
> 边界要划在一条**可论证的线上**（"我展示的每个数字都能独立核实"），
> 而不是"我大概没违规"。

### 3.3 陷阱：「我们不展示 X」≠「仓库里没有 X」

**这是原项目付出真实代价换来的教训**（2026-09-17 事故）：

仓库公开后第一次跑同步，`git add data/` 把缓存目录的 165 个文件（16 MB）一并提交进了公开仓库。
其中某条响应体含 **187 处被禁字段**——管线在解析时会剔除该字段，
**但缓存存的是剔除之前的原始响应**，于是整套合规拦截被绕过去了。

三个放大因素：

1. `.gitignore` 只写了一个目录，没想到还有第二个原始响应落盘点；
2. 缓存体是 **base64** 存的，明文 grep 查不出来，第一次扫描误报「干净」；
3. 合规拦截发生在**解析阶段**，而HTTP 缓存**早于**解析。

修法三道防线：gitignore 补目录 + workflow 用显式 pathspec + 提交前校验暂存区。

> **可迁移的判据**：
> **任何把上游响应落盘的地方（缓存、日志、artifact、调试转储）
> 都是一个独立的再分发面。加一个落盘点，就要重做一次合规评估。**

### 3.4 商标与素材

- 各对象名称为其所有者的商标，仅作**指称性使用**以标识被描述的对象，不表示关联或背书。
- 站内徽章是**原创**图形，**未使用任何厂商官方标识**。
- 素材逐条记录来源与许可，**再分发衍生作品时需保留署名文件**。
- 字体注意「星多 ≠ 开源」的陷阱：某 3000+ star 的中文像素字体实际是
  ¥7000 商业授权，且**版权声明禁止拆分**——而网页子集化恰恰就是拆分。
  改用 SIL OFL 1.1 的字体。

## 四、零 AI 依赖

### 4.1 表述

> 页面上所有文案由结构化字段套模板生成，**不调用任何 LLM**，也不展示上游返回的自由文本。

**两个理由**：

1. 信息永远不会被编造（LLM 写人物描述极易幻觉，而使命恰恰是展示真实状态）；
2. 双语没有翻译延迟——同一份数据渲染两次即可，新数据进来两边同时到位。

### 4.2 人类常识层一律做成**查表而非逻辑**

原项目有**两处**人类常识层，都是查表：

1. 厂商形象母题（机器读得出定价，读不出「它应该是一头鲸鱼」）；
2. 赛制的中文名与口径说明。

**关键设计**：未收录对象自动落到**兜底值**——
加不加系统都能跑，不会失败、不会白屏、不会阻塞管线。

> **可迁移的判据**：
> 「系统里唯一依赖人类常识的地方」要显式登记，并做成查表 + 兜底。
> 兜底存在的意义是：**这个站的承诺是零维护，任何硬失败都会破坏承诺。**
> 把兜底交给社区（提 PR 加一行）比交给一个需要续费的 API 便宜得多。

### 4.3 文案生成的层级：从宽到窄枚举

最容易想调 LLM 的地方（"一句话人设"），做法是**从宽到窄枚举「维度 × 限定域」，
找出这个对象排第一的最宽说法**。

产出的句子长这样：「开源模型里综合智力最强的模型」「十强里最划算的模型」。

**关键设计**：生硬来自泛化而不是模板——
「一款性能优秀的大语言模型」对谁都成立所以对谁都没用；
而「在某个域里排第一」这个条件**从结构上保证了同一句话在全站最多属于一个对象**。

## 五、护栏三层（本项目最可迁移的工程规范）

原项目的三层护栏，缺一层就会出现静默数据错误：

```
① 单元自测scripts/sync/selftest.ts   224 项断言，不联网，纯函数
② 校验闸门    scripts/sync/validate.ts  拒绝写盘 + 非零退出
③ 只读体检    scripts/qa/            17 个脚本，回答「为什么是这个结果」
```

### 5.1 ① 单元自测：测「错了也不报错」的那些函数

**选测标准很明确**：

>只测那些**错了也不会报错、只会静默产出脏数据**的纯函数。

具体清单（每条都对应一个真实踩过的坑）：

- 单位归一化（per-token → per-MTok）
- 日期格式（`YYYY-MM`，有的是精确日、有的是月）
- 上游把后缀当型号（`DeepSeek-R1 (May 2025)` vs `DeepSeek-R1`）
- 被禁数据源的字段剔除
- 闭源模型不得标「精确参数量」
- **校验闸门自己**

最后一条最容易漏：**闸门是「拒绝写盘」的唯一防线，它自己写错了防线就漏了。**

### 5.2 ② 校验闸门：宁可不动，别写坏数据

**原则**：合理性校验不通过就**拒绝写盘并保留旧数据**，绝不「带着旧数据继续往下走」。

原项目 20+ 条闸门，其中一条特别值得抄：

> **承重字段的相对跌幅闸门。**
> 2026-09-05 事故：上游把某个文件挪了位置并改了列名，
> 解析器找不到 → 某核心指标覆盖率 **38% → 0%**，
> 而闸门当时**只盯绝对跌幅**（"比上次少了 5 个百分点"），
> 对一个本来覆盖率就不高的字段**形同虚设** → 放行了。
>
> 现在改成按**相对跌幅**拦截（跌过一半就拒绝写入）。
>
> **教训：凡是前端排名依赖的字段，都必须有相对跌幅闸门。**
> 绝对百分点对覆盖率本就不高的字段毫无意义。

**闸门还必须自己被测**（见§5.1）。

### 5.3 ③ 只读体检：回答「为什么是这个结果」

**纪律**：全部**只读、离线、确定性**（同一输入产出同一输出）。

原项目 17 个，分类：

| 类型 | 例 | 回答的问题 |
|---|---|---|
| 影响面 | `flagship-rules.ts` | 改这条规则，全部对象会变什么？ |
| 解释单个 | `why-flagship.ts <id>` | 为什么这家派这个对象上广场？ |
| 过期检测 | `stale-flagships.ts` | 有哪些门面不是本家最新的？ |
| 数据体检 | `roster-signals.ts` | 广场每位门面有哪些数据、缺哪些？ |
| 视觉自检 | `shots.ts` | 三个断点批量截图 |
| 区分排查 | `verify-text.ts "某段文字"` | 是「没改干净」还是「浏览器缓存」？ |

最后那条特别值得抄——**它区分「代码没生效」与「你在看缓存」**，
这个区分能省掉大量无效排查。

### 5.4 QA 层的信息架构

**`AGENTS.md` 里写死了触发条件**（这是让规范真正生效的关键）：

```
用户说「更新数据」     → npm run sync && npm run sprites，然后按第三节检查清单核对
改了选拔/排名逻辑      → 先跑 flagship-rules.ts 看影响面
改了管线              → selftest.ts（224 项）+ tsc --noEmit + eslint
改了 UI               → 用 Playwright 在 1440/390 两断点截图自查
```

> **可迁移的判据**：
> 规范写在文档里没人看，**写在「什么情况下该跑什么」的对照表里才会被执行。**

## 六、架构决策与其代价

### 6.1 静态快照而非运行时拉取

**三个理由**（按重要性）：

1. **上游挂掉时网站照常显示上一次的好数据，永远不白屏**——运行时拉取做不到这一点。
2. **前端不碰任何 API key。** 没有密钥就没有泄漏风险，也没有需要人续费的东西。
3. **git 提交历史本身就是一套自动积累的快照库。**
   每天两次提交，一年后就有了七百多个时间点的完整状态。
   这正好可以喂给时间线页。**这个资产越早上线越值钱，而且完全免费。**

**代价**：数据新鲜度以半天计而非秒计。对一个信息站这个代价可忽略，
真要抢时效还可以随时手动触发一次同步。

### 6.2 可再生产物不入库

**606 张精灵图不提交进仓库**，构建时由「已提交的数据 + 已提交的设定表」确定性生成（约 7 秒）。

**理由**：合成器改一次绘制逻辑，就会一次性产生十几 MB 的新 blob，
几次迭代就能把仓库撑爆。构建时生成还有一个额外好处：
**产物必然与数据一致，不会脱节。**

### 6.3 身份层与状态层分离

| 层 | 烘焙进产物 | 理由 |
|---|---|---|
| **身份**（是什么） | ✅ 精灵图 | 只有对象本身变了才变 |
| **状态**（现在怎么样） | ❌ 前端现画 | 排名每天变；闪光30 天必然过期 |

好处：排名一变当场更新，**不需要重新合成任何一张图**；
而且前端层不受画布尺寸限制，能画得比烘焙时清楚得多。

**代价**：前端要知道元素位置，依赖产物里实测的锚点。
**不能硬编码百分比**——头顶高度会随体型、发型、有没有戴东西而变，
实测两个角色的颅骨顶能差 3 像素。

**握手信号**：产物清单顶层的 `overlaysBaked: false` 是两条管线之间的约定，
**前端读它而不是写死**——万一哪天合成器改回烘焙，前端不至于画重。
读不到清单时**保守地认为已烘焙，宁可少画也不要画重**。

### 6.4 布局与路由的坑

> **「本地点得通」不等于「哪都点得通」。**

原项目 `trailingSlash: true` 遇到末段含点就不补斜杠，
近四成详情页（215/556，slug 带点）在严格静态托管上 404。
本地 dev server 和 Vercel 都会做 `/x` → `/x/` 重定向，所以本地怎么点都是对的。

**修法**：slug 里的点转连字符+ 两条自检锁住。

> **验证要用最笨的文件服务器**，而且要对着**导出的文件名**核链接，
> 别只看浏览器点得开。

## 七、文档体系：HANDOFF 制度

原项目文档 4,518 行（7 篇），其中 `HANDOFF.md` 1,086 行。
**结构值得照抄**：

```
HANDOFF.md   给下一个接手的人（无论是人还是 AI）
             ├── 一、这是什么
             ├── 二、当前状态（已完成 / 关键覆盖率 / 未完成）
             ├── 三、快速上手（日常维护一览 / "更新数据"怎么做 / 体检脚本）
             ├── 四、不可违背的原则   ← 最重要
             ├── 五、贯穿全站的模式
             ├── 六、踩过的坑          ← 第二重要
             ├── 七、代码地图（文件 → 职责）
             ├── 八、容易被误改回去的决策
             ├── 九、已知缺口（诚实列出做不到的）
             ├── 十、接着做什么（按优先级）
             └── 十一、产品负责人的偏好
```

### 7.1 两个必抄的小节

**「不可违背的原则」**：每条都要能回答「改动前必须先确认是不是真的想推翻它」。

**「踩过的坑」**：排序标准是
> **按「不知道就一定会再踩一次」排序。**

这一节的价值无法用代码复现——它记录的是**试过但行不通的方案**。
原项目里「刻意不做的选择」「曾经破坏过原则又回滚」的记录，
比成功路径的信息密度更高。

### 7.2 第四节「产品负责人的偏好」：把模糊的反馈沉淀成规则

这一节记录的是**历次反馈沉淀下来的硬约束**，例如：

- 「阅读舒服是最重要的」→ 字号已整体上调三次，正文 14px 起，别再往小调
- 「不要在页面上放解释性文字」→ 凡是需要解释的词，**换掉它**而不是解释它
  （西岸都会 → 国外、东方城邦 → 国内、庄园 → 全部模型）
- 「任何规则重复的线条压在文字后面都会被否掉，无论透明度多低」
- 「这一排不放源码链接」→ 但页脚下半段的署名区那行不算，两者不冲突

**为什么这节值得抄**：产品决策如果不沉淀成规则，
下一轮开发会把它当成个人偏好而忽略掉。**「他明确说过的，别再撞」**这句话本身就是文档价值。

## 八、已知的「不要以为是 bug」

原项目专列一节列出做不到的部分（覆盖率上限、口径限制、某维度永久缺失等）：

- 编程覆盖 45% 左右，**而且已经到顶了**——瓶颈已从数据源转移到「这些厂商压根没被人测过」
- 速度维度**不存在，且核实过确实补不上**（唯一系统性实测的源禁止再分发）
- 「每家一间屋」与「全球榜首」是两回事，会短暂不一致
- 某些门面是数据说了算，不一定是常识里的旗舰
  （因为该厂商没有任何对象有成绩，规则只能退到「最新 + 价格档」）
  这是零人工干预的代价，**不是 bug**

> **可迁移的判据**：
> 明确区分「做不了」与「坏了」。
> 前者要写进文档并给出「为什么补不上」的核实过程；
> 后者才进 issue。
> 混在一起会让接手的人反复尝试已经证明不可行的路。

## 九、可直接迁移的检查单

从参考项目提炼，面向「新建一个数据驱动静态站」：

### 立项时

- [ ] 核心承诺写下来（本项目：**发布后不需要任何人维护**）
- [ ] 列出系统里**唯一依赖人类常识**的地方，并设计成查表 + 兜底
- [ ] 确认数据的**法律状态**：能否再分发？是否有竞品限制？是否需署名？

### 数据层

- [ ] 每个字段都有**字段级**来源记录（不是「机型级」）
- [ ] 多源时建立**仲裁链**并逐字段记 provenance
- [ ] 判断数据源是否**真的相互独立**（原项目发现两个聚合器是同源的，互为兜底是无效的）
- [ ] 空值有**专属视觉形态**，与「值是 0」一眼可辨
- [ ] 承重字段有**相对跌幅**闸门（不只是绝对百分点）
- [ ] 闸门自己被测试

### 护栏

- [ ] 单元自测：覆盖每个「错了也不报错」的函数
- [ ] 只读体检脚本：至少 3 个（影响面 / 解释单个 / 数据体检）
- [ ] 规范写成**「什么情况下该跑什么」的对照表**，放进 agent 说明文件

### 工程

- [ ] 产物与数据分离，产物可由数据确定性重建
- [ ] 静态托管的路由行为要用**最笨的服务器**验证
- [ ] 落盘的上游响应（缓存/日志/artifact）全部纳入合规评估

### 文档

- [ ] HANDOFF：这是什么 / 为什么长这样 / 接着做什么
- [ ] **踩过的坑**按「不知道就一定会再踩」排序
- [ ] 已知缺口：明确区分「做不了」与「坏了」
- [ ] 产品负责人的偏好沉淀成规则

### 发布

- [ ] 内容变化判据用**内容指纹**，不是 `git diff`
- [ ] 生成物不进库；产物可重建
- [ ] 部署验证要抽查深层页、页面内相对引用、关键数据页
- [ ] 「页面渲染正常」≠「页面能用」——**端到端点一遍**

## 十、附：本项目不做的事（示范「不做什么」）

原项目明确列出刻意不做的：

| 不做 | 理由 |
|---|---|
| 造合成总分 | 参数拼出来的「综合性能分」是编造 |
| 雷达图 | 多维对比的可读性远低于分位横条 |
| 随机拼装角色 | 用户判为「具有随机性」——形象必须与社区认知强相关 |
| 商业字体子集化 | 版权声明禁止「拆分」，而子集化就是拆分 |
| 解析型号里的版本号 | 在多数对象上失灵的启发式比没有规则更糟 |
| 用「最近 N 天」圈当代 | 45/60/90 天都试过，都会误伤 |
| 走「合并分」聚合 | 跨赛制分数永不混算（见下） |

**跨赛制永不混算**这一条值得单独说明，因为它是「全站最容易被无意破坏的一条」：

同一个对象换一套评测脚手架就能差二三十分（同一能力，
难度更高的那个基准中位数低 34分）。所以：

1. 分位池按**「赛制 + 测量方」**分组（只按赛制分还不够——同一赛制下不同测量方不是同一分布）；
2. **量纲不可混**（百分数 / Elo / 自定义标度不是一回事）：
   曾经漏掉一个分支，某自定义标度被印成了「2176.9%」——
   **一个看起来像数据错误、实则是渲染错误的数字，比缺数据更伤可信度。**
3. 大厅卡片**不显示原始分数、不显示名次，只显示分位档**——
   原始分数不可比，名次也不可比（池子大小从 6 到 85 不等，
   「6 个里第 2」和「25 个里第 2」都显示成「第 2」）。**分位档是唯一跨池可比的表达。**
