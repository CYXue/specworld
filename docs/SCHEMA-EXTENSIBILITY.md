# 架构可扩展性审计：「发现新可量化参数」时会发生什么

> 2026-10-13 · 回答的问题：**当我发现某个电子产品的新功能特性可以列为量化参数加入对比时，
> 数据结构会不会已经写死、加不进去？** 参照系：准绳（Baseline）的 EAV 七表模型。
> 本文档是决策材料，结论待用户在三个方案中选定后落地。

---

## 一、先把「写死」拆开——specworld v2 的四层审计

「数据结构写死」其实是四个不同层面的问题，扩展成本完全不同：

### L1 数据层（schema 字段表）——**活的** ✅
加一个参数 = `data/schemas/phone.json` 的 `fields` 数组加一行 JSON（path/label/unit/type/range/group）。
闸门、校验、质量报告、编辑器/纠错表单的字段下拉**全部自动识别**，零代码。
这与准绳「attributes 表加一行」**等价**——因为 specworld v2 的 schema 本来就是数据，不是代码。

### L2 校验层——**活的** ✅
`validateSpecValue(field, value)` 按 schema 声明的 type/range 泛化校验，新字段自动进闸门、自动进
质量报告的填充率统计。无需任何改动。

### L3 展示层——**半死** ⚠️（真正的痛点在这）
`src/lib/fields.ts` 的 `specGroups` 是**手写策展行**，详情页 SpecTable 与对比矩阵共用。
新字段不会自动出现，需要手动加渲染行。现状有两道护栏：
- **渲染对账闸门**（selftest 第 246 项）：漏加 → selftest 红，报「要么渲染要么进豁免清单」；
- 哨兵值实测走 `toPhoneView → specGroups` 同一条链。
即：**漏加会被大声拦住（不再是静默失效），但每次加字段仍是一次代码改动**。
半死的意思：死不了（闸门守着），但没活（没有自动化）。

### L4 类型系统——**最深的冻结点**，但是刻意设计的 ❄️
type 封闭集 `{number, string, boolean, enum, array:number, array:string, object, array:object}`
写死在三处（validateSpecValue / 编辑器前端校验 / 纠错表单 coerce）。
**但这是权衡而不是缺陷**：类型只在「参数要参与算术/排序/区间闸门」时才需要；
怪异形态一律用 string 保留官网原文（`display.refreshHz="1-120"` 先例——强转 number 会丢语义）。
真要加新类型 = 三处各加一个 case + 文档，一次有界改动（已列为类型系统扩展点）。

### 两个特殊冻结点（B 也一样，属正常范畴）
- **身份字段**（顶层 id/brand/line/name/modelCode…）：加一个 = types.ts + 数据契约 + 解析器，
  本质是**契约迁移**而非「参数扩展」。准绳的 products 表列同样写死——等价，不算输。
- **多实例嵌套子结构**（如 camera.rear 数组里每颗镜头的 role/mp/aperture/ois）：
  给镜头加一个新子属性（如传感器尺寸）= 对象契约变更。准绳的处理是**拍平**：
  把「主摄像素」「长焦像素」各自建成独立 attribute 行——多实例的每个实例就是一行数据。
  两种建模的取舍见下文方案对比。

## 二、准绳（Baseline）是怎么做到「加参数零代码」的（实证）

`baseline-db-format-spec.md` §2.3 + `CompareService.ets`：

1. **参数就是数据行**：`attributes` 表（id / category_id / group_name / name / sort_order /
   name_en / group_name_en），加参数 = INSERT 一行；
2. **渲染完全泛化**：CompareService 按 group 遍历 attributes 动态出对比行，**没有任何逐字段的
   界面代码**——所以「写死的地方」根本不存在；
3. **代价（关键！）**：`values.value` 是纯 TEXT（"14英寸"、"120Hz"），**没有类型系统、
   没有区间闸门、没有 quantifiable 标记**——因为它不做排行、不做分位、不做能力条。

**结论：准绳不是「解决了写死」，是把架构做薄到没有可以写死的地方。**
它用「放弃类型严谨」换「完全灵活」。而 specworld 的类型/区间/quantifiable 是数据诚信
与榜单功能的地基（range 闸门抓过 164.6mm 折叠机、type 防过 refreshHz 类型漂移），
**不能为了灵活把地基拆了**——所以正确方向不是照抄 EAV，而是把准绳「泛化」的思想
只用在**展示层**，保住数据层的严谨。

## 三、三个方案（按协作铁律并列呈现，待用户选择）

### 方案一：准绳式彻底泛化（specGroups 变 schema 驱动引擎）
详情页/对比表按 schema 全量渲染：group → field 逐行走通用格式化器（type→文本），
现存的策展合并行（「尺寸」合并三维、「亮度」合并典型/峰值、camera.rear 拆四行）
全部改用 schema 里的声明式元数据表达（如 `view.merge` / `view.formatter`）。

- ✅ 新参数**真零代码**：schema 加一行，详情页/对比表/编辑器/纠错表单全部自动出现；
- ✅ 与准绳同构，渲染对账闸门从「必要护栏」降级为「可选」；
- ❌ 重构面大：动详情页 + 对比表 + 能力条的数据源，回归风险集中；
- ❌ array:object（camera.rear）的漂亮拆行本质仍需 per-field 格式化声明——
  「完全泛化」在复杂字段上并不免费；
- ❌ schema 开始携带展示关注点（merge/formatter），数据与视图的边界变模糊。

### 方案二：混合——「默认泛化 + 声明式策展」（我的推荐）
specGroups 重构为**引擎**：schema 里每个字段默认按 type 自动渲染（新字段自动出现——核心诉求达成）；
需要精修时在 schema 字段上加**声明式 view 元数据**（如 `"view": { "merge": ["body.heightMm","body.widthMm","body.thicknessMm"], "label": "尺寸", "formatter": "dimensions" }`），
引擎按元数据合并/改名/定制格式。没有元数据的字段吃 type 通用格式。

- ✅ 「发现新参数 → schema 加一行 → 页面自动出现」成为默认路径（用户的核心诉求）；
- ✅ 保留现有全部策展质量（合并行/拆行/改名都还在，只是从代码搬进声明）；
- ✅ 渲染对账闸门保留作护栏（豁免清单随声明式化逐步缩小）；
- ✅ 与 UNIVERSAL-CATALOG 既定方向一致（新品类页面直接吃 specs+schema）；
- ❌ 中等重构（一次集中改 specGroups + 搬移现有合并行声明），需要回归验证；
- ❌ schema 文件稍变胖（多 view 元数据）。

### 方案三：维持现状（双处手动 + 闸门兜底）
加参数 = schema 加一行 + specGroups 加一行，漏加由渲染对账闸门大声拦截。

- ✅ 零改动风险，闸门已保证「最多吵你、不会静默丢」；
- ❌ 「写死」问题在结构上依然存在，每字段一次代码改动，字段多了会烦；
- ❌ 与「全品类全品牌」的长期野心方向相反（品类多了以后展示层手写量线性膨胀）。

### 决策对照表

| 维度 | 一 准绳式泛化 | 二 混合（推荐） | 三 现状+闸门 |
|---|---|---|---|
| 新参数成本 | 零代码 | 零代码（精修时才写声明） | schema+代码两处 |
| 展示质量 | 依赖声明式元数据表达力 | 保留现有全部精修 | 现状（已验证） |
| 改动风险 | 大 | 中 | 零 |
| 类型严谨（区间/quantifiable） | 保留（数据层不动） | 保留 | 保留 |
| 与准绳的距离 | 同构 | 思想同源、保留严谨 | 无 |
| 建议时机 | 想一步到位时 | **推荐：下一个迭代窗口** | 短期收尾期 |

### 不变的共同底线（三方案都成立）
- L1/L2 数据与校验层**现在就是活的**，任何方案下「发现新参数 → schema 加一行」都成立，
  差别只在它何时出现在页面上；
- 类型系统保持封闭集 + string 兜底（忠实原文），扩展点已文档化；
- 身份字段与多实例嵌套属契约迁移，两项目同构，不作为「写死」缺陷记账。

## 四、最优解（用户追加问题：「完全不考虑兼容性，最优是什么」2026-10-13）

**全声明式字段字典 + 泛化引擎**（方案二的彻底版 + 两处结构升级）。
核心：参数的一切语义（数据 + 展示）进字典（纯数据文件），代码只剩不认识任何具体字段的通用引擎。

五层结构：

| 层 | 内容 | 加新参数时 |
|---|---|---|
| 数据字典 `schema.json` | path/label/单位/分组/类型/区间/quantifiable/dir + 四态语义 | 加一行 |
| 视图字典 `view.json`（与数据字典分离） | 展示语义：显示/合并/格式化器/参与对比 | 不动（默认全显示） |
| 值对象 | specs 扁平容器 + provenance + 四态例外（现状保留） | 不动 |
| 泛化引擎 | 一个引擎服务详情/对比/编辑器/纠错表单；type→格式化器为封闭可加注册表 | **永不改** |
| 类型系统 | 封闭集 + string 忠实原文兜底 | 极少（仅排序/算术需求时） |

两个关键设计：

1. **对比引擎只依赖「相等」，不依赖「排序」**。用户定的「只标差异、不判好坏」在架构上是
   决定性的：不需要比大小 ⇒ 任意类型只需结构相等判断 ⇒ 所有类型无特判进对比表。
   `dir` 从对比引擎退役，只剩榜单一个消费者。

   > **澄清（2026-10-13 用户问：这与榜单/筛选的排序是一回事吗？——不是）**。
   > 「不依赖排序」只针对**对比引擎**。全站操作分两类引擎：
   > | 引擎 | 依赖什么 | 覆盖的功能 |
   > |---|---|---|
   > | **相等类引擎** | 结构相等 / 包含 / 存在性 | 对比差异检测、筛选分面、四态判断、表单校验 |
   > | **序类引擎** | 数值类型 + `dir` + `quantifiable` | 榜单排序、SORTS_LITE 排序条、能力条（bounds 归一化） |
   > - 相等类引擎**全类型泛化**：新字段自动进对比表；筛选维度由字典声明 `facet: true` 自动开启
   >   （现状 `facets.ts` 的 DIMENSIONS 硬编码身份分面，与 specGroups 同模式，归入同一次泛化改造）。
   > - 序类引擎**显式声明制**：新字段要进榜单就在 schema 声明 `dir`（不声明=只进对比/筛选）。
   >   string 形态的序类适配（如 `refreshHzNumber()`）也走字典声明 `orderDeriver`，不污染对比引擎。
2. **多实例用「子字典」**。字段可声明 `cardinality: list` 并挂子字典（每颗镜头/每个接口的
   属性各自是带类型区间的字段行）。发现镜头该有「传感器尺寸」→ 子字典加一行 → 自动出现。
   借准绳「每实例一行」的拍平招式但保留类型区间——灵活与严谨同时拿到。

为什么不选纯 EAV：纯 EAV 把语义推进自由文本（"14英寸"），类型校验/区间闸门/量化排名/
能力条全部失效——用户的数据诚信红线（忠实原文/区间/溯源）在纯 EAV 里无处安放。
最优解 = EAV 的开放性 + schema 的严谨性的合体。

落地路径（未来执行时）：从现状增量平滑——先把 view 语义从 specGroups 搬进视图字典，
再拆文件；渲染对账闸门全程护航。

## 六、「两处结构升级」与遗留最优解清账（2026-10-13 晚，全部落地）

最优解第四节承诺的两处结构升级 + 审计澄清注里的两项遗留，已全部实施：

1. **多实例子字典（cardinality:list + subfields）✅**
   - `camera.rear` 声明 5 个子字段（role enum / mp range[0.1,250] / aperture / ois / sensorNote）；
   - `schema.mjs`：validateSchema 结构校验（子 path 挂父前缀、禁嵌套、enum 必有 values）+
     `subfieldsOf/subfieldMap/validateListField` + array:object 深校验（**逐项逐子键**：
     mp 越界/role 拼错/多余键全拦——此前 array:object 是无深校验的无底洞）；子项缺键=null 语义合法；
   - selftest 正反测（含 schema 自身结构断言）；真实数据 62 台过闸。
2. **参数级筛选（schema facet:true → 分面自动纳入）✅**
   - schema 声明 `facet:true`（首发 5 个：5G/NFC/eSIM/刷新率/振动马达）；
   - `facets.ts` 泛化：DimKey 放宽 string、`DIMENSIONS = 身份维度 + facet 字段`（消费方
     FilterBar/CompareView/BrandView **零改动**）、`emptyFilter` 动态、`valueOf` 相等类分支
     （boolean→'true'/'false' 显示是/否、string 原文、缺失→未公布）、URL 键=字段路径（身份维度
     仍单字母）、facetOf 排序安全兜底；非法值丢弃反向测过。
3. **序类适配器字典化（orderDeriver）✅（最小闭环）**
   - schema `orderDeriver:"refreshHzNumber"` 声明 + `fields.ts ORDER_DERIVERS` 注册表 +
     `orderDeriverFor(path)`；selftest 对账（声明必须有实现、null→null 不冒充）。
   - SORTS_LITE/榜单保持**序类策展 UI**（有意不字典化：变化频率低、ABILITIES 对账闸门已守语义）。
4. **有意不做（留档）**：身份字段进字典（=契约迁移，两项目同构）；ART 导向策展（
   导出图/搜索权重）留代码；SORTS_LITE 序类策展。
