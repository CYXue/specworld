## 二、真正重要的五条架构差异

### 差异 1：仲裁层 vs 单源直连 —— 参考项目最硬的一块

参考项目的管线不是「抓下来写进去」，是**七步**，其中第3 步是全项目的核心：

```
抓取(ETag 条件请求) → 归一化(单位/日期/SPDX) → 【字段级仲裁 + provenance】
→ 合理性校验闸门 → 原子替换
```

**字段级仲裁**的意思是：同一个字段有多个上游候选时，按可信度优先级选，并记录**这个值是从哪个上游来的**（`provenance`）。

比如 `contextWindow` 的兜底链（实测覆盖率 68.8% → 98.8%）：
```
models.dev → LiteLLM → OpenRouter → Vercel Gateway
```
`pricing` 同理（57.9% → 90.6%）。

本地的 `products.json` 是**单源直连**：华为官网一个字段只有一票，没有第二来源，官网不公布就是空。
`docs/PROBE-FINDINGS.md` 记录的就是这件事——官网取数可行，但覆盖率有上限。

**这一条不能照抄，因为前提不同。** 参考项目能从 8 个源仲裁，是因为它的字段（参数量、价格、上下文）
有一堆公开数据库在互相印证；手机的 PPI、厚度、电池容量只有厂商官网知道，**没有第二个源**。
照搬仲裁层只会造出一个永远只走第一票的空壳。

>可迁移的是**结构**不是**内容**：`provenance` 字段值得抄。本地现在的 `sources` 字段只有来源名，
> 没有到「哪个字段来自哪个源」的粒度。加了之后，将来补第三个品牌（小米/三星）时，
> 同一个字段的两家官网说法不一致，你能立刻看出分歧在哪。

### 差异 2：自测层 —— 本地已补齐（2026-10-03）

参考项目 `scripts/sync/selftest.ts`，**224 项断言，不联网**，专门测那些
**错了也不报错、只会静默产出脏数据**的纯函数：

```
单位归一化 · YYYY-MM 日期 · 发布日期的两个实测反例 · 人工分析字段剔除
闭源模型不得标 exact 参数量 · 合理性校验闸门本身
```

最后一条尤其关键：**校验闸门自己也要被测**。闸门是「拒绝写盘」的唯一防线，
它自己写错一个边界值，整条防线就漏了。

本地的解析器踩过同一个坑，`validate.mjs` 里有明确记录：
> 旧解析器把 PWM调光频率（1440 / 2160）和分辨率数字（2622）当成了刷新率，
> 这种错值能一路畅通地发布出去，只能靠闸门兜。

**当时是靠肉眼发现、然后补一条闸门 `refreshHz: [48, 240]` 兜住的。** 但那次的根因在解析器，
闸门只是把症状按住。如果有自测，`parse.mjs` 里那个解析函数当时就该有一条断言挡住。

**差距的本质（已填平）**：本地曾经是「出事 → 补闸门」，2026-10-03 起已补 `scripts/selftest.mjs`（79 项断言，CI 首个 job），转为「写代码 → 写断言 → 事前拦住」，与参考项目一致。

### 差异 3：只读体检层（QA scripts）—— 本地已补齐（2026-10-03）

参考项目 17 个只读脚本，全部离线确定性，加起来回答一个问题：**「为什么页面是这个结果」**。
```
why-flagship.ts某家为什么派这个模型上广场
stale-flapships.ts       还有哪些门面不是本家最新的
roster-signals.ts        广场每位门面有哪些数据、缺哪些
value-rank.ts    性价比排序的影响面
match-gap.ts    缺口有多大
shots.ts 三个断点批量截图
```
`AGENTS.md` 里还写死了一条：**改了排名逻辑先跑 `flagship-rules.ts` 看影响面**。

本地现已补齐（2026-10-03）：`scripts/qa/` 下 `why-champion` / `coverage` / `stale-lineup` 三件套，全部离线确定性，回答「为什么这台是榜首」「改了档位影响面多大」，且复用 `buildChampions` 单一真源，不会与页面结论分歧。现在想回答这些问题，
只能手工跑管线 + 手翻 dist HTML。这是**当前最高频的隐形成本**。

### 差异 4：精灵图不进仓库 + 状态层 DOM 化（本地已于 2026-10-03 对齐）

参考项目 606 张精灵图**不提交**，构建时由 `models.json` + 角色设定表确定性生成（7 秒）。
理由写得很直接：合成器改一次绘制逻辑就产生十几 MB 新blob，几次迭代仓库就撑爆。

拆分更狠：**精灵图只烘焙「模型是什么」（身体/发型/服饰），
「模型现在怎么样」（皇冠/光环/闪光）由 DOM 现画**。
排名一变当场摘冠，不用重新合成 PNG。体积从 18.4 MB 降到 11.5 MB。

本地 `data/sprites/` 已**不再入库**：2026-10-03 起精灵图改由 `scripts/sprite/generate.mjs` 在管线构建期确定性生成（几何由屏幕对角线/厚度/后摄数算出），`data/sprites/` 写入 `.gitignore`。与参考项目做法一致，**规模增长不再是爆点**。

### 差异 5：指纹 —— 本地比参考项目强，别改回去

本地 `fingerprint.mjs` 比参考项目的 `toy/fingerprint.ts` 多做了一件事：

**站点指纹 = 数据指纹 × 模板哈希。**

理由：页面是「数据 × 模板」的产物，改任一都要重新发布。
组合式指纹天然绕开了「在 HTML 里剥离时间文本」的难题——
那种做法容易把业务日期（发布日期）一起误删。

本地还踩过一个参考项目没踩的坑，已修并写进注释：
> 归一化行尾再哈希。Windows 上 checkout 出来是 CRLF，Linux CI 上是 LF，
> 同一份代码会算出两个模板指纹 —— 本地推一次 CI 就判「站点变了」，两边来回空转。

**这一层不用抄参考项目，参考项目该抄本地。**

### P0 补完的即时回报

自测第一版跑起来**当天就抓到一个静默 bug**：

```
parseRefresh('60 Hz / 90 Hz 屏幕')  →  只取到 60，90Hz 整段被丢掉
```

根因：`/` 被当子句分隔符切开，而 `^…Hz$` 的严格锚定让第二段匹配失败。
原文 `LCD，支持 60 Hz / 90 Hz 刷新率` 是华为官网**真实原文**（`changxiang-80` 在用）。

**危险等级：高。** 60 落在闸门区间 `[48, 240]` 内 → 闸门不拦 → 脏数据静默发布。
这正是 §6.5 说的那一类错误：**「少取了一个值」闸门一律放行**。

已修（放开裸Hz 写法的中文尾巴，`parse.mjs` 里有注释说明为什么安全）。

**这次修复对现有 当时 60 台数据无影响**（指纹未变，`7159f85fc42b2b06`），
因为在库的那台写法带了「刷新率」二字能命中另一条分支——属于防御性修复。
但下一次官网改版改文案就会踩上。

## 四、怎么让下一个项目更快

现在这两个项目的关系是「**抄了架构，没抄工程化**」。
`docs/AUTOMATION-RECIPE.md` 已经把自动化的部分沉淀出来了（含迁移检查单）；自测层（`scripts/selftest.mjs`，79 项断言）与体检层（`scripts/qa/` 三件套）也已在 2026-10-03 补齐，下一项目可直接复用，不必再踩一遍坑。

### 4.1 抽一个 `world-factory` 模板仓

建议建`C:/aiwork/deepseek/dsh/world-factory/`，内容是**两项目的交集骨架**：

```
world-factory/
├── templates/
│   ├── vanilla-static/        # 零依赖版（手机项目用这个）
│   └── next-export/           # Next.js 版（大模型项目用这个）
├── shared/
│   ├── fingerprint.mjs        # 本地版指纹，通用（数据×模板组合式）
│   ├── validate-gate.mjs      # 闸门骨架：范围表 + 覆盖率 + 相对跌幅
│   ├── stable-json.mjs        # 参考版：递归键名排序 + -0 归一
│   ├── selftest-harness.mjs   # 零依赖断言小框架 + 覆盖清单
│   └── publish-matrix.md      # Pages / Vercel / Toy 三种目标的条件差
├── docs/
│   ├── RECIPE.md              # 从零到自动化的完整配方（合并两家长处）
│   ├── PITFALLS.md            # 两项目踩过的坑合并成一份（参考 25+ / 本地 8）
│   └── CHECKLIST.md           # 新项目启动检查单
└── init.mjs                   # 一条命令生成新项目骨架
```

关键收益：新项目第一天就有自测、闸门、指纹三件套，
不必像手机项目一样先裸奔三轮才补上防线。

### 4.2 把三层的实现抽出来（这是"更快"的核心）

| 抽象 | 从哪抄 | 改造点 |
|---|---|---|
| **闸门框架** | 本地 `validate.mjs` 的注释式设计（每条闸门必须回答「防哪种故障 + 误报概率」） | 范围表抽成配置，域相关值由新项目填 |
| **指纹** | 本地 `fingerprint.mjs`（数据×模板组合式） | 换数据文件名与模板目录 |
| **自测框架** | 参考 `selftest.ts` 的 224 项模式 | 断言框架用零依赖 `node:assert` 重写，域相关断言留模板占位 |
| **体检脚本** | 参考 `scripts/qa/`（只读、离线、确定性） | 每个项目写自己的 3个 |
| **稳定序列化** | 参考 `stable-json.ts` | 直接抄，一个文件 |

### 4.3 一份配方文档该长什么样

参考项目 `HANDOFF.md` 1086 行里有两节价值最高：**「不可违背的原则」**与**「踩过的坑」**。

- **「不可违背的原则」**（数据诚信 / 合规红线 / 零AI 依赖 / 跨赛制分数永不混算）
- **「踩过的坑」**（数据侧 + 视觉侧，25+ 条，每条带原因）

**这类文档不能自动生成，必须人写。** 本地已在 2026-10-03 补 `PRINCIPLES.md`（不可违背原则 + 明确不做清单），下一项目可直接复用，不必从零写、也不必重新回忆华为官网的每个假设。

## 五、为什么不迁移到 Next.js

本地是手写 mjs 模板（`build.mjs` 1117 行 + `ui.mjs` 569 行）出 76 页静态 HTML。
参考项目用 Next.js 16 + React 19 + Tailwind 4。看起来落后一大截，**但本地在这条路上更值**：

| 维度 | 手写 mjs 模板 | Next.js 16 |
|---|---|---|
| 本地现有存量 | **1686 行已跑通** | 全部重写 |
| 产物 | 3.8 MB / 76 页，零依赖 | 引入 React 19 + Tailwind 4 构建链 |
| 装依赖 | **零** | 约 300 MB node_modules |
| 本地约束 | GitHub Pages 单端 | 需要 Vercel 或 EdgeOne 才能部署 |
| 加i18n | 字典套模板（本来就该这么做） | 加 `src/app/en/` 路由层 |
| 加交互 | 手写 DOM 事件（已内联搜索索引，可行） | React 组件天然 |

**结论：迁移的收益是「省手写模板的活」，成本是重写 1686 行 + 引入构建链 + 换部署目标。**
真要减模板代码，**先把 `ui.mjs` 的片段函数按组件拆开**就够了，不需要换框架。

唯一值得考虑迁移的场景：本地要加**用户可交互的复杂功能**（如在线筛选排序的排行榜、URL 状态同步），
纯 DOM 手写会开始难维护。那时迁 Next.js 有意义。
