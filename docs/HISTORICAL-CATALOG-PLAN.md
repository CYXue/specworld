# 历史机型工程（立项文档）

> 状态：**M1 验证已完成（2026-10-25），路线已定**——小米主路线改走 ③/④，
> view 接口降级为机会性补充源（必须带身份校验）。原因见「M1 验证结果」。

## 一、背景

2026-10-25 用户裁决取消滚动窗口（`WINDOW_START = 2000-01-01` 等效全量），
官网**当前在售目录**全部进站（1215 台）。但官网只挂当前在售：
小米商城目录池 200 个 id、华为官网品类页——下架即无入口。
「小米/华为所有历史机型」不在当前采集范围内，需要独立工程。

**苹果不需要本工程**：苹果老产品线（1976–2023）已由用户数据层 `add-product`
全量收录在册（892 台中占大头），且有对比页矩阵兜底。

## 二、数据源候选（按优先级）

| 来源 | 覆盖 | 结构化程度 | 风险 |
|---|---|---|---|
| ① `api2.order.mi.com/product/view`（既有适配器） | **已验证（M1）：不可作为主源**——下架商品三种结局并存，见下节 | 与在售同构（「关键参数」） | 高：id 会被回收复用，新商品顶掉旧商品 |
| ② 小米商城商品详情页 `mi.com/shop/buy/detail?product_id=NNNN` | 同 ①（同一套 id 体系） | 同上 | 同 ①：清空/回收风险相同 |
| ③ ZOL 规格库（`detail.zol.com.cn`） | 华为 + 小米全历史机型，带完整规格表 | 半结构化（页面表格，需解析器） | 中：采集规模大；页面结构改版需归档复现机制；**数据使用边界需人工确认** |
| ④ 京东商品页 | 下架商品页多数仍可访问，带参数表 | 半结构化 | 中：同 ③，另需处理促销价噪声 |

## 二·一、M1 验证结果（2026-10-25，探针 `_work/_probe-xiaomi/m1-view-delisted.mjs`）

用 6 个下架商品 id + 1 个在售对照打 view 接口，三种结局并存：

| 结局 | 样本 | 表现 |
|---|---|---|
| **清空** | Xiaomi 10 (#20304)、11 Ultra (#13649)、Civi (#14999) | HTTP 200 但业务码 **-50011「商品不存在或未上架」**——下架即从接口清除 |
| **残留** | REDMI Note 11 Pro (#10000330) | 完整返回（18 项关键参数）——下架后数据仍在 |
| **id 回收** | 小米手环10 (#10726)、智能家庭屏10 (#18397) | 返回**完全无关的新商品**（口袋打印相纸、鱼缸滤芯）——**id 被复用，映射不稳定** |

结论：
1. view 接口**不是历史档案**，不能据此重建小米历史目录（主力机型清空、无清单可枚举）。
2. 残留部分可作为**机会性补充**：拿 ZOL/京东确认过 id 的机型，用 view 接口取结构化关键参数。
3. **新增一条硬纪律**：凡经 view 接口取数，必须校验返回 `name` 与目标机型一致
   （id 回收会让同 id 返回别的商品，不校验 = 静默采错数据）。这条要写进接入 checklist。

## 二·二、直抓通道受阻实测（2026-10-25，M2 开工时）

计划中的 ③/④ 批量直抓全部被拦，四通道实测结论：

| 通道 | 结果 |
|---|---|
| ZOL 列表页/规格页（curl） | 302 → `service.zol.com.cn/checking` 人机校验，cookie 流程后 404 |
| ZOL（headless Chrome，等 30s） | 仍卡「防刷验证」页——自研墙识别无头浏览器 |
| pconline 产品库 | 直连与 web_fetch 均 **503** |
| GSMArena | Cloudflare **Turnstile** 挑战，headless 不过 |
| Wayback 存档 ZOL 页 | CDX 两次空响应、availability API 无响应——无可用的 ZOL 存档 |
| 中文维基百科 | 网络层不可达（000） |

**路线改定（M2 生效）**：批量直抓不可行 → 改用本项目已验证 339 次的
**检索取证式采集**：按机型逐台检索（ZOL/IT之家/中关村在线等出现在搜索结果里的
规格摘要），子代理分批产出结构化 JSON，逐台带 sourceUrl 与身份校验。
ZOL 直连通道留档：拿到可用会话（登录 cookie/代理出口）后可重启，接口形态见上表。

## 三、范围与优先级

第一阶（小米，复用既有基础设施，成本最低）：
1. **验证** view 接口对下架 id 的可用性（半天，决定 ①② 是否成立）；
2. 手机全历史线（数字系列 / REDMI K / Note / Civi）——对比矩阵式数据源已验证过该路线；
3. 平板 / 笔记本 / 穿戴（既有映射器直接复用）；
4. 米家电历史款（复用 appliance 映射器）。

第二阶（华为，必须走 ③/④ 半结构化源，成本最高）：
1. 手机（Mate / Pura / nova 系列）——规格页解析器已有，但源页面结构不同，
   需要新解析器 + golden 断言（**先写断言再改代码**纪律不变）；
2. 平板 / 穿戴 / 音频；
3. 智慧屏 / 显示器 / 路由。

## 五·一、粒度与收录口径（2026-10-25 用户裁决）

1. **全站统一「每型号一条」粒度**：同型号的存储/颜色配置在记录内以档位数组合并
   （如 iPhone 11 一条记录、storageGb=[64,128,256]），不按 SKU 拆多条。
   苹果数据层本就是该粒度（892 条 = 892 个不同型号/代际，双探针复核：剥存储/颜色后
   仅 1 组同规格重复 Macintosh SE，已去重）——苹果 892 vs 华为/小米 200+ 的差距
   是**品类广度**（苹果 50 年 × 17 品类，desktop 282 / laptop 191 / display 61 /
   input 42 / storage 31 / printer 8），不是 SKU 粒度差。
2. **生态链/贴牌不收录**：米家有品生态链、华为智选贴牌等非官方自营品牌不进库；
   只收官方自营品牌（苹果 / 华为 / 小米 / 荣耀）。米家（小米自营品牌）家电按此口径收录。

## 五、纪律（本工程不得违反的红线）

1. **数据诚信**：源没有的字段一律 `null`，不估算、不用同系列他机填补。
2. **日期取证**：每台历史机型必须有 `release-dates.json` 条目（sourceUrl 真实可查），
   缺日期进待收录队列，不猜。
3. **解析层必须配 golden 断言**：新源解析器上线前先写夹具，`npm run selftest` 不通过不发布。
4. **闸门区间覆盖全量真实数据 + 余量**：老机型量级差异（如 2019 年路由器、2016 年手环）
   打穿区间时放宽区间并留 note，不弱化闸门。
5. **判据是内容指纹**：历史批次入库同样走「指纹判变化」，禁止用 `git diff`/时间戳判据。
6. **使用边界**：③④ 属第三方站点数据，采集与展示的使用边界（版权/ToS）
   在 M1·五 阶段由人工确认后才开工，不留「先采了再说」的口子。
7. **身份校验（M1 新增）**：凡经 view 接口（或任何 id 寻址接口）取数，必须校验
   返回的商品名与目标机型一致——小米商城 id 会被回收复用（#10726 手环10 → 口袋打印相纸），
   不校验 = 静默采错数据。
