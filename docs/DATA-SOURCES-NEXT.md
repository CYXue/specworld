# 第二数据源立项：规格归档通道（提案）

> 状态：立项提案，未实施。本文档回答「macDB 通道榨干之后，剩余数据缺口从哪补、值不值得、怎么做」。

## 1. 背景与现状

2026-10-20 批次后，macDB（macdb.cn）作为第二票源已经榨干：

- 871 台映射（三轮纠错：高置信 → 基底唯一 → 人工研判 + 错配清洗），参数三通道补齐；
- 剩余空缺属于两类：① macDB 页面本身没有的值；② 77 台本站有意不收的变体（非数据问题）。

**本站可达性实况（941 台）**：电池 mAh 104、充电功率 ~113、
老机型重量 ~442/941。这些字段 macDB 只在少数现代设备页提供。

## 2. 候选源评估

| 候选 | 覆盖 | 结构化程度 | 合规 | 结论 |
|---|---|---|---|---|
| support.apple.com 归档规格页（specs URL 重定向 → archive.org） | 全部历史 Apple 机型 | 官网原文，35 章节粒度 | 官方一手 | **首选**，但 archive.org 本网络不可达（2026-10-15 实测），需代理通道 |
| EveryMac | 全部 Mac 机型 | 表格化好，但含第三方推断字段 | 社区站，需逐字段甄别 | 备选；只取「官方可核验」子集 |
| apple.com/archive 历史产品文稿 | 部分历史机型 | 官方原文 | 官方一手 | 与归档规格页合并评估 |

纪律不变：**只取官方可核验值，查不到就留「—」**；每条 provenance 精确到来源 URL。

## 3. 范围（按价值排序）

1. **电池容量（mAh/Wh）**：现代 iPhone/Watch 官网早已不公布 mAh，历史机型归档页有；
2. **充电功率 / 充电方式**：老机型页面有「适配器」段落；
3. **老机型重量/尺寸**：Mac 归档规格页有完整 body 数据；
4. **华为侧**：不在本立项范围（官网一手已有，见 `scripts/normalize/` 华为通道）。

## 4. 工程方案（复用 macdb-sync 的骨架）

- 新增 `scripts/archive-sync/`：对账（archive URL 清单 ↔ 本站 id）→ 折叠（只填空缺）→
  provenance 标 `apple-archive`（SourceId 需新增枚举，同 macdb-cn 的接入路径）；
- 映射表人工研判 + selftest 健康度断言（复用 `scripts/macdb-sync/` 模式：
  悬空引用 / slug 唯一 / 品类一致 / era 冲突 / 年份偏差五道防线）；
- 网络前置条件：archive.org 可达性（代理或镜像），否则通道建好也空转。

## 5. 验收标准

- 折叠后 `npm run selftest` 全绿 + `--data-only` 闸门全绿（既有纪律）；
- 折叠只填空缺字段，provenance 全部带归档页 URL 可回溯；
- 覆盖率报表（`npm run quality`）对目标字段的提升可量化（电池 mAh、充电功率两列为先）。

## 6. 不做什么

- 不做字段级仲裁层（单源无第二票可投，见 PRINCIPLES）；
- 不抓第三方站的推断值（EveryMac 的跑分/升级建议等）；
- 不为覆盖率往 macDB 已榨干的字段上重复投入。
