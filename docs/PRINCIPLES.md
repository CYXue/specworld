# 不可违背原则（PRINCIPLES）

> 这份文档是本项目工程实践的「总纲」。任何重构、加品牌、接数据源之前，先读它。
> 它对应参考项目 `AI 大模型世界` 的 `HANDOFF` 文档里那种「不可违背原则 + 踩坑清单」的角色，
> 但内容是本项目自己踩出来的，不是照抄。
>
> 维护规则：每一条原则都必须能说出「违反它会出什么真实故障」。说不出就不要加。

---

## 1. 数据诚信（最高优先级）

**规则**：解析不出来就是 `null`。不写 `0`、不写 `-`、不写空串、不写平均值、不写估算值。

**为什么**：用户打开页面是为了比参数。一个编造的「0 mAh」比「官方未公布」危害大十倍——
前者假装知道，后者诚实说不知道。本项目所有 `null` 都是可追溯的「官网真没有」（见 `normalize/index.mjs`
文末 `REPORT_NOTES`：苹果从不公布电池容量/RAM/充电器功率，华为 50 台里 20 台官网没有处理器章节）。

**边界**：跨口径永不混算。亮度峰值 < 典型时，两个都判为不可信（置 `null` 并记 note），
绝不拿一个去「修正」另一个。

---

## 2. 零 AI 依赖（文案与判定的硬约束）

**规则**：页面文案 100% 由「数据 × 模板」生成，不调用任何 LLM。每一个显示出来的值都能在
`data/products.json` 的某个字段里找到出处。

**为什么**：站点要离线可看、要确定性可复现、要能回答「这个数从哪来」。LLM 生成的内容不可追溯、
可能幻觉，且让「体检结论 == 页面结论」这一核心保证失效。

**范围**：连「一句话定位」（`buildPersona`）都是纯查表 + 排序 + 字符串拼接，不碰模型。
i18n 英文版也必须人审后填，不靠机器翻译硬凑。

---

## 3. 跨口径不混算

**规则**：不同测试条件 / 不同来源口径下的数字，只并列展示，不进任何排序或均值。

**实例**：
- 厂商标称续航（苹果「视频播放 34 小时」vs 华为「视频播放 X 小时」）测试条件不同 → 只并列，不排名。
- 字段级仲裁不能照抄参考项目：手机参数只有官网一个源，照搬参考项目的 8 源仲裁只会造出永远只走第一票的空壳。
  可迁移的是 `provenance` 结构（记录「这个数来自哪个源 / 哪种口径」），不是仲裁逻辑。

---

## 4. 闸门纪律（拒绝写盘，不是拒绝报错）

**规则**：`validate.mjs` 只做一件事——在数据变坏的那一刻拒绝写盘，保留上一版快照。
每条闸门必须能回答：①它防的是哪种真实故障？②误报（把好数据拦下来）的概率多大？

**为什么**：上游官网改版、某机型页面结构变了、某字段突然全空，都会静默产出残缺数据。
闸门是最后一道墙。但**闸门只查数值越界与少量契约字段**——解析器犯的错往往在合理区间内，
所以必须有自测层兜底（见第 6 条）。

**关键认知**：**闸门自身也会误报**，所以它必须被审计测试覆盖（`selftest.mjs` 专门测 `validate`）。
本项目真实踩过：`resolutionPx` 是 `{w,h}` 对象，规范化层登记子路径 `.w`，闸门查父路径 → 60 台全报假警。

**闸门自身两种失效都要防**：
- **太吵（误报）** — 如上，`60 台全报假警`；
- **太静（漏报）** — `check-conventions.mjs` 匹配 `base: './'` 时，
  命中的却是配置文件里那行**说明注释**，导致真的把 `base` 改成 `'/'` 也检不出来，
  **零报错**。这类静默失效更危险：闸门显示绿灯但不设防，你会开始信任它。

修法统一是**把闸门反向测一遍**：故意注入违规 → 必须报出 → 改回 → 必须恢复绿灯。
匹配「代码文本」的闸门还必须**先剥注释**，否则示例会变成通行证（见 `PITFALLS.md` P7）。

**闸门只查能机器判定的条款**。注释质量、命名是否贴切、目录分得是否合理都不查——
闸门一旦开始报「审美问题」，就会被整体忽略。**只管能判的。**

---

## 5. 指纹纪律（用户看得见的东西变了才发布）

**规则**：发布判据不是「文件变了」，而是「用户看得见的内容变了」。

**机制**：
- `data/products.json` 带着一串运行时刻字段（`generatedAt` / `lastSeenAt` / `listedAt` / `fetchedAt`），
  每次跑都在变，与官网数据无关 → 直接哈希会制造空提交。所以先**剥运行时刻**再算数据指纹。
- 站点指纹 = 数据指纹 × 模板哈希（模板改版也要重发）。模板哈希只哈希真正参与构建的 `.mjs`，
  **排除纯文档型的 `.ts`**（否则改个注释就误触发一次白发的 Pages 重发）。
- 行尾归一化后再哈希，避免 Windows CRLF / Linux LF 让同一份代码算出两份指纹、两边来回空转。

---

## 6. 自测纪律（测试覆盖倒置是头号风险）

**规则**：最脆弱、上游改版最先崩的地方必须有单测，而不是等肉眼发现。

**为什么**：两次刷新率事故（`2622×1206` 分辨率被当 2622Hz、PWM 调光频率被当刷新率）都是肉眼发现的，
而肉眼只会发现最明显的那一个。所以 `selftest.mjs` 专测「错了也不报错、只静默产脏数据」的纯函数，
并接进 CI 第一个 job。品牌映射层（600+ 行，最脆弱）有 golden-file 测试：固定 raw → 固定产物，
逐字段比对。

**判据补充**：闸门挡不住「少取一个值」——结果落在合理区间内一律放行。这是自测层存在的根本理由。

---

## 7. 品牌注册表单一真源

**规则**：受支持品牌（id / 元数据 / 刘海类型 / 短标签）只在一处定义（`scripts/brands.mjs`），
其余处一律查表，禁止散落 `'apple'/'huawei'` 字面量分支。

**为什么**：加第三品牌（小米 / 三星）时，散落的硬编码要改 10 处，极易漏。集中后新增品牌只改一个文件。
写入 `data/products.json` 的 `vendors` 形状必须与历史快照逐字段一致，否则数据契约字节会变。

---

## 8. 零依赖与可重建

**规则**：全链路只用 Node 内置模块（`node:*`），无 `node_modules`，CI 无装包失败点。
入库的只有 `data/` 与代码（`_work/`、`dist/`、`data/sprites/` 都 gitignore，产物可由仓库确定性重建）；任何人跑 `node scripts/pipeline.mjs --offline`
（约 4 秒）就能从缓存重建全部产物。

**为什么**：依赖越少，十年后还能跑的概率越高。本项目定位 demo，但工程纪律不降级。

---

## 9. 依赖源纪律（本地走镜像，提交的 lock 必须干净）

**规则**：`package-lock.json` 里的 `resolved` 主机名**只允许** `registry.npmjs.org`。
本地 `npm install` 可以走国内镜像（快），但提交前必须规范化。

**机制**：`npm run lock:check`（只读检查）/ `npm run lock:fix`（只换主机名）。
`lock:check` 已挂在 CI 第一个 job，push 时当场拦截。

**为什么**：lock 是要提交进仓库、并在 GitHub Actions 上 `npm ci` 的产物。
本机 registry 指向 `registry.npmmirror.com`（装包快），于是**每次本地装新依赖都会把新条目写成镜像地址**。
lock 里混进镜像后：
- 连不上该镜像的环境（境外 CI、别人的机器、公司网络）`npm ci` 直接失败；
- 偏离开源仓库惯例，也让 diff 出现同一依赖两种主机的混排。

**关键认知（容易搞反）**：这**不影响构建，也不影响包内容**——每个依赖的 `integrity`（sha512）
才是内容正确的保证，镜像与官方源是同源同步、tar 包字节一致。
所以问题**不在"安全"（integrity 照样兜底），而在"可移植性与 CI 稳定性"**。
别用「怕镜像投毒」当理由说服人装 `.npmrc` 锁死官方源——那会让本地安装变慢，是错误的权衡。

**为什么不用 `npm install --package-lock-only --registry=...` 重生成**：
那会重写整份 lock（实测会丢字段、结构可能残缺）。正确做法是**只替换 URL 的主机名**，
其余字节不动——`lock:fix` 改完后与原始 lock 逐字节一致，可验证。

## 明确不做（避免范围蔓延）

- **不迁 Next.js**：1671 行手写模板已跑通，迁移收益不抵成本。
- **不扩品牌**：当前只做华为 + 苹果两家「完全对齐」的窗口，扩品牌是独立的未来方向（见第 7 条铺垫）。
- **不接第三方跑分**：手机参数只有官网一个信源，第三方分数不进契约。
- **不做像素小人 / 装饰性视觉炫技**：站点是参数对比工具，不是展示页。
